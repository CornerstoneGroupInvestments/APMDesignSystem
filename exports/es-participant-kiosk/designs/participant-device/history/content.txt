P |This document provides the detailed technical design for the APM Participant Kiosk solution, part of the APM digital workplace transformation program. H1 |2. Overview
P |APM delivers Workforce Australia and Inclusive Employment Australia employment services under contract with the Department of Employment and Workplace Relations (DEWR). Participants attending APM sites nationally require access to computing facilities for job search, resume preparation, government service interaction and training. The current device fleet has several problems, including very old hardware, slow internet connections and a lack of manageability.
P |This document defines the detailed design for the Participant Kiosk solution. It replaces the existing shared device model with a standardised architecture: Dell hardware running Windows 11 Enterprise as a locked-down, multi-app Assigned Access device. The device signs itself in. There is no participant account, no password and no lock screen credential: the device powers on into a restricted session presenting Microsoft Edge and LibreOffice. Intune handles device management and policy enforcement, and Entra ID holds the device object only.
P |Every session is ephemeral. After ten minutes of inactivity the session ends and the device restarts, and every restart purges the participant profile, so the next participant starts on a clean device. Participants carry their documents away on their own USB media or send them to their case manager from personal webmail. The design meets Right Fit for Risk (RFFR) accreditation requirements for protecting participant personal information.
P |This document covers the physical Participant Kiosk only. The Standard User SOE, Developer SOE, Privileged Access and ES take-home device use cases are addressed in separate design documents.
H2 |2.1 Scope
P |• Physical Participant Kiosk provisioning and configuration (Dell hardware, Windows 11 Enterprise)
P |• Windows Autopilot self-deploying enrolment into the existing APM corporate tenant, creating a device object only
P |• A named local session account (Kiosk-[SERIAL]) created on-device by a signed remediation and signed in automatically, with no participant credential and no sign-in step
P |• Multi-app Assigned Access restricted user experience (Microsoft Edge, LibreOffice, File Explorer scoped to Downloads, Desktop and removable drives, Zscaler tray, TeamViewer)
P |• LibreOffice Fresh deployed as an Intune Win32 application, configuration locked by policy, patched by Patch My PC
P |• Microsoft Edge hardening, managed favourites, and PDF viewing in Edge
P |• Device-based licensing: Microsoft Intune device licence, Windows 11 Enterprise E5, Microsoft Defender for Endpoint P2
P |• Conditional Access, browser and web-filtering controls that prevent any Microsoft 365 sign-in from a Participant Kiosk
P |• Session hygiene: ten-minute inactivity sign-out and restart, and a full purge of participant data on every restart
P |• USB storage access for participants to carry documents to and from the device
P |• Zscaler web filtering and logging
P |• APM Windows SOE Hardening Standard inheritance, Edge CIS Level 2 hardening, and the ISM Windows 11 baseline applied at device scope
P |• Security and RFFR compliance alignment
P |• Managed bookmark deployment across job search, government, support, training and transport categories
P |• Decommissioning of the cloud components of the retired kiosk solution, raised as a separate change request

H2 |2.3 Guiding Principles
TBL|1416,7944
TH |**ID**||**Principle**
TR |Zero Trust||The device is the only identity. It is Entra-joined, Intune-managed and continuously assessed against a compliance policy. No corporate identity can authenticate from it: Conditional Access blocks every APM account on Participant Kiosk hardware.
TR |Ephemeral by Default||No participant data persists beyond the session. Edge browsing data never reaches the disk, downloads live only inside the profile, and the profile is purged on every restart.
TR |Least Privilege||The participant runs as a standard local account with Edge, LibreOffice and File Explorer scoped to Downloads, Desktop and removable drives. No settings, command prompt, task manager, installation or cloud sign-in.
TR |Simplicity||The end-user experience is frictionless. The device powers on directly into the participant session. There is no username, no password and no credential displayed anywhere.
TR |Compliance||The architecture meets RFFR requirements for the handling of participant personal information, aligning with ISO 27001 and the ASD ISM, and inherits the APM Windows SOE Hardening Standard V3.0.

H1 |3. Business Architecture
H2 |3.1 Business Context
P |The Participant Kiosk solution is a response to three target business outcomes: consistent data privacy across all sites, standardised device management at scale, and compliance with RFFR accreditation requirements under the Workforce Australia Service Deed and the Inclusive Employment Australia Service Deed.
P |Two business changes follow. Participants do not sign in, which removes the operational burden of credentials on a public device and the risk of a participant using someone else’s session. Documents are now created in LibreOffice on the device rather than in a browser-based Office suite, which removes the need for the participant to hold any Microsoft identity and keeps every document under the participant’s own control on their own media.

H1 |4. Application Architecture
H2 |4.1 Solution Overview
P |The Participant Kiosk solution is a single tier: a physical device running Windows 11 Enterprise as a locked-down multi-app Assigned Access endpoint. B |**Setting Name**: CDG-W11-REM-Idle Restart-P-1.0
B |**Setting Type**: Win32 application, two files (installer plus separately signed watchdog). H3 |4.3.10 Remote support access model
P |Remote support is required. Site staff cannot troubleshoot a device in a public area, and the fleet is national, so the alternative to remote support is a truck roll for every fault. TeamViewer is retained as the remote-support tool and is allow-listed in both Assigned Access and App Control. Because the estate hardening standard disables every other remote-access path (Remote Assistance, Remote Shell, inbound Remote Desktop), this is a documented variation to that position rather than an oversight, and the controls below are what make it acceptable.
P |**This is not Remote Desktop.** RDP, Remote Assistance and Remote Shell stay disabled by the inherited baseline; installing TeamViewer changes none of them. Nothing listens on TCP 3389 - the session is established outbound to the vendor service on 443, so no inbound path into the default-deny VLAN exists. RDP could not serve here anyway: the session account credential is known to no one, and a console takeover would disconnect the participant rather than assist them.
P |**Alternatives assessed.** Quick Assist is a Store application on a fleet with the Store off, and cannot reach an unattended device. Microsoft Remote Help would remove the third-party tool but is per-helper licensed and assumes a signed-in user context; recorded as the preferred replacement to reassess if APM licenses it.

TH |**Aspect**||**Design**
TR |Support scenarios||Two. Assisted support, where a support operator joins the session the participant is signed in to, with the participant present. Administrative support, where a support operator signs in with a support account to a device with no participant session, for diagnosis and remediation
TR |Consent for assisted support||Attended only. The participant must accept the incoming connection at the device. Unattended access is not enabled for the participant session
TR |Unattended access||Permitted only for the administrative scenario, on a device with no participant present. It is the mechanism that allows a support operator to reach an idle device, typically outside site hours
TR |Support account||APM-PKAdmin, a local account on that device only, not a privileged-tier (xy or zz) identity and not the Assigned Access session account. P |The residual risk is that a compromised TeamViewer operator account, or a compromise of the vendor’s platform, yields access to a Participant Kiosk. The blast radius is one device, or the fleet, holding no corporate information, carrying no corporate credential, on a network segment with default-deny egress and no route to APM corporate systems (5.3), and from which no corporate identity can authenticate (7.2.4). Multi-factor authentication on operator accounts, no shared connection passwords, no file transfer, per-device LAPS credentials and Sentinel session logging reduce the likelihood; the network position and the absence of any corporate identity on the device limit the consequence.

H1 |6. Information and Data Architecture
H2 |6.1 Information Model
P |The Participant Kiosk solution introduces no persistent data store of any kind. There is no cloud store, no mailbox, no OneDrive and no server-side profile. P |• Participant input: resumes, cover letters, job applications and form submissions, created in LibreOffice or typed into a website

H3 |7.3.1 Relationship to the APM Windows SOE Hardening Standard
P |The Participant Kiosk is a Windows 11 Enterprise endpoint and is governed by the same document as every other APM Windows device: the APM Windows SOE Hardening Standard V3.0 (internal), which carries 748 controls across 11 Intune policies, benchmarked against the ASD Windows Hardening Guidelines, the Microsoft Windows 11 v24H2 baseline and the Microsoft Edge security baseline v139. H2 |8.3 Disaster Recovery and Resilience
P |The architecture is inherently resilient because it is stateless:
B |No persistent data. There is nothing to recover. Every session starts from clean device state by design
B |No cloud identity. There is no account to restore, no password to reissue and no directory dependency for a device to be used
B |Device failure. Replace the device, register its hardware hash in Autopilot, and it self-provisions with no data migration
B |Site failure. Devices at other sites are unaffected; there is no shared component between sites other than the Microsoft and Zscaler services
B |Tenant-level failure. A Participant Kiosk continues to run its current configuration and remains usable for local document work; policy and application changes resume when the service returns

P |**Delivery Optimization**
P |Each site has a 20 Mbps link and up to five devices, and that link is shared with the participants using it. Delivery Optimization is the control that stops five devices each pulling the same monthly update across it: one device downloads from Microsoft and its neighbours take the bytes from that device over the site LAN. A Windows 11 cumulative update is roughly 700 MB to 1 GB, so peering that works turns about 5 GB per site per cycle into about 1 GB, and a LibreOffice release does the same again at a few hundred megabytes.
P |**Why the peer boundary is the subnet, not a group.** Delivery Optimization has to be told which devices count as neighbours. Group mode derives that from an Active Directory site, a domain SID, a DNS suffix, a DHCP option or the Entra tenant. This fleet is Entra-joined with no Active Directory, so the first two do not exist, and deriving the group from the tenant would make a device at one site treat a device at another as a peer and attempt discovery across the WAN, which is worse than no peering at all. Each site is already a discrete /26 from the Meraki template (5.3.1.1), so the subnet is the correct peer boundary and LAN mode expresses it with no group plumbing to maintain.
P |**Own policy, not Autopatch.** Autopatch does not manage Delivery Optimization. Delivery Optimization is configured as a dedicated fleet policy, independent of the Autopatch registration above. The bandwidth ceilings below are tuned to a 20 Mbps site link shared with members of the public; applying those ceilings to a corporate office would throttle staff devices, and applying the estate office values here would let a patch download crowd out a participant.

P |Two network conditions have to hold for any of this to work, and both are outside Intune. P |LibreOffice is patched on the same rhythm but through a different channel: Patch My PC publishes each Fresh release into Intune as a superseding Win32 application, which installs on the pilot ring first and on the fleet three days later (5.2.4). Zscaler and TeamViewer are updated as controlled changes, TeamViewer together with its App Control publisher rule.
P |**Vulnerability management position.** Vulnerability exposure on this fleet is managed by automated patching rather than by a remediation backlog. Two channels cover everything installed: Windows Update for Business rings deliver the operating system, Microsoft Edge and the Defender platform on a daily 03:00 cycle, and Patch My PC delivers LibreOffice as each release ships. Both land inside the ISM two-week window for operating system and application patching, and the expedite policy covers actively exploited vulnerabilities inside 48 hours. Defender for Endpoint vulnerability management reports the installed software inventory and CVE exposure for every device, and those findings are reviewed at the existing weekly vulnerability review meeting (9.2) rather than in a process specific to this fleet. Because the device installs nothing after provisioning and App Control (WDAC) permits only five publishers to execute, the exposure surface is fixed and known: anything Defender reports is one of four applications or the operating system itself.
H2 |9.4 Decommissioning the Retired Kiosk Components
P |The kiosk solution in place today carries identities, cloud resources, policies and a domain that this design does not use. Dormant components are an unowned attack surface and a source of audit findings, so each is removed under change control rather than left in place (DR-016).
P |**The decommissioning is raised as a separate change request** and is not specified in this document. Two reasons. A decommissioning activity is a change to the running environment, with its own approval, sequence, rollback and evidence obligations, and it does not belong inside a design that is approving a new build. More importantly, a material part of what was built is not being deleted: the Azure landing zone, its private DNS resolution, the Log Analytics workspace and the test network were built to the pattern the Standard User AVD SOE and the Developer AVD SOE both consume, and those components are retained, renamed and handed over rather than removed. Sorting that out is a change request with two receiving designs, not a section of this one.
P |Reference: APM Change Request - Kiosk Decommissioning (designs/kiosk-decommission). It carries the full disposition register (delete, retain, repurpose, rename) for every component, the components the AVD use cases inherit, the RFFR evidence exports and DEWR notification, the seven-stage sequence, and the rollback and validation position.
P |Two dependencies run from this design into that change request. Decommissioning does not start until the Participant Kiosk pilot has passed the test plan in 9.6, so that no fallback is removed while it might still be needed. And the Zscaler identity objects are not removed until the provisioning workshop under DR-013 has concluded, because that workshop determines which of them the replacement forwarding model still requires.
