# Project: APM - 4 SOE AVD/Nerdio Implementation

This design system supports an ongoing **Twiki Corp** engagement for **APM** (Advanced Personnel Management) - the **Digital Workplace / AVD program**: standardising end-user computing onto **Azure Virtual Desktop (AVD)**, orchestrated via **Nerdio Manager for Enterprise**, managed by **Intune + Entra ID**. Output includes design docs, knowledge-base articles, the project plan, and status reporting. Contract end: **30 September 2026**.

## Scope - 5 AVD use cases + network foundation
Originally scoped as 4 SOEs; now **5 use cases** (Privileged Access added). Build order:
0. **Network foundation** (enabler) - site network (APM-KIOSK VLAN 73, hidden SSID, Meraki, Palo Alto, Zscaler IPSEC) + reusable Azure hub-spoke pattern (Australia East).
1. **Participant Device** (P1, formerly "Job Seeker Kiosk"; **design V1.0, 4 Aug 2026** - a new baseline that supersedes the kiosk design V1.6 in full) - Dell hardware, **Windows 11 Enterprise** (no longer IoT LTSC), multi-app Assigned Access with **automatic logon to a Windows-managed local account** (no participant identity, no credential, no lock-screen display), **device-based licensing only** (Windows 11 Enterprise E5 + Intune device licence + Defender for Endpoint P2), **LibreOffice installed locally** instead of Office for the web, Microsoft 365 access **blocked outright** at three layers, and a restart-based session purge. The whole credential pipeline (Key Vault, Function App, Automation, Cloud PKI, rotation) is removed and decommissioned. **The code-signing certificate is still the master gate** (device scripts + App Control signing). WDAC/RFFR remains the dominant control.
2. **Standard User SOE** (P2, **detail design V2.0, 23 Aug 2026** - a rewrite answering an 11-comment stakeholder review, built on the APM template's exact 33 headings) - Win11 Enterprise multi-session, pooled, Australia East only, Nerdio, FSLogix on Azure Files Premium, one SOE two channels (thick client or AVD). **Join type is the one place the two channels diverge: the existing thick clients are hybrid joined to on-premises AD; the new AVD session hosts are Entra ID joined.** ADFS is being decommissioned. No address range is reserved for AVD - a /23 must be allocated (G-02), and that gates every network object.
3. **ES take-home device** (P3, formerly "CTA") - Participant Device pattern + midnight reset + Zscaler-on-device for off-site Wi-Fi.
4. **Privileged Access** (P4, new) - PAW-style hardened image, two tiers (Priv `zz` / High-Priv `xy`), YubiKey 5C NFC FIPS + PIM. Only production-access path.
5. **Developer SOE** (P5, draft V0.1) - permissive AVD image, Azure Image Builder pipeline, no production path. GA ~mid-Oct (past contract end on current resourcing).

## Two rules that keep this repeatable

**One fact, one home.** A value lives in exactly one file; every other mention cross-references it. This applies to design tokens (`tokens/`), compliance rules (`policies/compliance-rules.js`), environment facts (`policies/environment-config.js`), corpus facts (`reference/eslz/`), craft rules (`reference/design-capability-briefing.md`) and datasets alike. The three `reference/*.md` skill documents each carry a "Canonical sources" block naming what they own; read it before editing one. Two copies of a value is a defect waiting to happen, and it is the failure that ships a document contradicting itself.

**Source in, curated out.** `uploads/` is disposable upload scratch. Every ingest ends by copying the source to its durable home (`policies/` for policy and standard documents, `reference/environment/` for as-builts, `reference/eslz/` for corpus parts, `reference/apm-document-templates/` for APM's own templates), updating that folder's README index, and rewiring any `file:` path that pointed at `uploads/`. Never cite an `uploads/` path from a tool, a register or a design.

## Change records
**Emergency and normal change records use `templates/emergency-change/`** - `EMERGENCY-CHANGE-TEMPLATE.md` (blank, with the writing rules), `example-planb-ca-usb-office-test.md` (worked example), `README.md` (index and rationale). Never write a change record as prose. **Rules:** one action per line, imperative verb first, the exact object named every time (policy name, group name, device, account - never "the policies") · **every risk line states the risk AND what bounds it**, because a risk with no bound is an open issue · every test has an objectively true-or-false pass criterion · **the test plan tests THIS change only**, everything else goes in Out of scope. Five fields the APM form lacks and the template adds: why this is an emergency, rollback deadline, rollback trigger and who calls it, implementer verification separate from business testing, and Out of scope. Three failure modes it exists to prevent, all found in a real record: a test plan broader than the change (false coverage), ambiguous rollback wording ("remove the group from the policies" when the exclusion list was meant), and a temporary exclusion outliving the group it excluded (risk CR-05 in the decommissioning CR). Every object named must resolve against the relevant register before submission.

## Documents contain facts, not commentary - MANDATORY, every document, every revision

A shipped document (design, change request, KB article, report) contains settled facts and technical content only: values, decisions as decided, options actually considered and ruled out where relevant, configuration as specified, dependencies and instructions the executor must follow. It never contains commentary in the assistant's own voice narrating how or why a decision was reached, how strong an argument is, or how the document itself was authored or revised - that narration happens in chat, never in the shipped document.

**The Decision Register records decisions stakeholders make, never the assistant's rationale for a solution.** A row states the specific decision as made or as required, options actually considered if useful (as fact, not argument), and who decided or must decide it - a named role or body, never "recommended" or "the best option is." A decision no stakeholder has made yet is an open item awaiting their decision, not the assistant's proposal with supporting reasoning.

**Forbidden in the document body, anywhere:** any sentence describing the document's own construction, genre or template (\"Built on <template>,\" \"This is a change request, not a design,\" \"structured so it can be ticked off\") - a document opens directly with its content, never with a note about what kind of document it is, what it was built from, or how it differs from another kind. A genuine citation needed to support a specific fact (\"per DR-010, Job Seeker Detailed Design V1.3\") is not the same thing and stays \u00b7 any sentence in the assistant's own explanatory voice narrating its reasoning or rationale for a solution (\"this reframes the argument from X to Y,\" \"the strongest single sentence available to defend,\" \"worth citing because it...\", \"recommended,\" \"the best option is\") \u00b7 sentences narrating the document's own revision history (\"Correction carried into this version,\" \"Revision this version,\" \"corrected this version,\" \"not previously captured,\" \"Reduced this version\") \u00b7 hedges and suggestions (\"you could also,\" \"I'd recommend\").

**The one place version-to-version change is recorded:** a Document Control / Version History table, near the top of the document, one row per version, one brief factual line per row (what changed, not why) - e.g. "Log Analytics workspace disposition changed from Repurpose to Delete," never "changed to Delete because repurposing risked a stale rule." **Every row records a change to the DESIGN, never to the document's authoring**: "Palo Alto firewall removed from the egress path" is a version row; "editorial pass", "prose reduced to fact statements", "figure re-exported", "explanatory text removed from 4.2" and "cross-references converted to hyperlinks" are authoring activity and belong in chat, not in the document. Where a revision changed only the writing, fold it into the next substantive version. Every document that will be revised gets this table from V1.0, including change requests.

**Cover fields state the solution and the programme, not the technology you last worked on.** `Program Name:` is `Standard Operating Environment Program` - it covers all five SOE use cases. Never write `AVD/Nerdio Implementation` on a document whose solution uses neither, and the ES Participant Kiosk (a physical Dell device) uses neither. `Project Name:` is the solution's real name as APM calls it: **ES Participant Kiosk Solution**.

**Still permitted, because it is fact or record, not assistant commentary:** the Decision Register convention (`guidelines/detailed-design-standard.md`) stays exactly as used - options APM actually considered and ruled out, stated as fact, with a one-line reason each · settled decisions and their one-line rationale as a fact of record · operational dependencies stated flatly ("Confirm before revoking - not reversible") · source citations ("Found in <document>").

## Design document standard - MANDATORY for every design we produce
**Every design document, HLD, DDD or solution design in this project follows `guidelines/detailed-design-standard.md`. Read it before starting one - no exceptions, no "lite" version.**

The bar: **a build engineer can construct the solution from the document without asking a question, and an approver can say yes without asking for more information.** Three rules:
1. **Show the settings, not the intent** - actual values in tables (setting name as it appears in the product, value, rationale). Never "traffic is inspected on egress"; always `0.0.0.0/0 → 10.100.0.68`, applied to which subnets, BGP propagation on/off.
2. **Diagram every structural idea** - capability impact, system context, interface sequence, technology placement, network topology, deployment path, information flow, security zones. Always on the design system's diagram kit (`tokens/diagrams.css`, `.dgm-*` classes) so every document looks like the same program.
3. **Logical order, front-loaded argument** - business → application → technology → information → cyber → availability → service management. Anything a reviewer would challenge (BYOD access, standing privilege, an unmet requirement, an accepted risk) is argued openly and early, never left to be discovered.

**Two rules that apply to every design, every revision, no exceptions** (full text: `guidelines/detailed-design-standard.md` 2a and 2b):
- **Write like a person, not like a machine.** No "it is important to note", "leverage", "utilise", "robust", "seamless", "comprehensive", "delve into", "In order to", or a paragraph opening with "Additionally/Furthermore/Moreover". No rule-of-three flourishes, no paragraph that restates its own opening sentence at the end. Active voice with a named actor, short sentences, a number instead of an adjective. If you would not say it to a colleague at a whiteboard, rewrite it.
- **Every cross-reference carries the section number AND its name, as a live hyperlink.** In the DSL write `[[5.3.4]]` and nothing else; `docx-builder.js` resolves it to "5.3.4 Routing" and links it to a bookmark on that heading, so the name is never hand-typed and can never go stale. Works in prose, bullets, numbered steps and table cells. `UNRESOLVED [[xref]]` in the build log is a build failure. References into a companion document in another tier stay plain text and name the document ("Technical Configuration Document, 12.6").

**§5.3 Network is the section that fails most often** and must carry all nine of: naming convention · address plan incl. reserved ranges · subnet allocation with masks and NSGs · routing with next-hop IPs · DNS resolver and private zones · named egress FQDNs · NSG rule baseline · connectivity/resilience spec · a build-level diagram showing the CIDRs.

**Pipeline (do not rebuild by hand) - `templates/detailed-design/authoring/`:** `apm-master.docx` (APM cover set, document control, disclaimer, Contents, real heading styles) · `docx-builder.js` (splices generated body into the master) · `content-example.txt` (worked-example content + the DSL reference) · `example-figures.html` (nine example diagrams + Tweaks panel) · `qa-checks.js` · `figs/*.png`. The standard's §5 documents the DSL, the build steps, and the traps already hit (doubled bullets from `ListParagraph`, `pStyle` self-closing with a space, cutting on the wrong "Introduction" and deleting the TOC, missing `xmlns:wp`/`xmlns:r`, one document per `run_script` call).

**Every design and figure set also passes the consistency scan.** `templates/detailed-design/authoring/consistency-check.js` - `scan({dsl, figuresHtml, figFiles, staleTerms})` must return `ok: true`. It catches the defect class `qa()` cannot see: a statement that was true when written and went stale when another section changed. Ten checks: **TREE** (top-level sections run 1..n with no gaps; every heading has a parent - this is what catches an H1 accidentally consumed by an edit) · **XREF** (every "see 4.3.9" resolves to a real heading) · FIGSEQ / FIGREF / FIGFILE · **DUAL** (a policy classified as both inherited and excluded, unless an explicit cross-reference reconciles them) · **COUNT** (a stated count vs the rows of the table below it) · FIGTXT (section refs and retired terms inside figure captions and notes) · STALE (retired terms anywhere) · ORPHAN (an artefact named once - informational, not a failure). Run it after every content edit, not just before shipping.

**Before shipping any document or figure set, load `qa-checks.js` and run `qa()` - it must return `ok: true`.** Eight scans: overlaps · WCAG AA contrast across the whole page · figure overflow · **box-level clipping (`scrollHeight > clientHeight` on every `.dgm-box`/`.dgm-heat`/`.dgm-lbl`/`.dgm-note`, so a box that hides its own last line cannot pass)** · literal escapes and em dashes · orphaned wire labels · legend coverage of every connector style · arrows occluded by boxes (including buried arrowheads). Do not hand-write these checks. **When resizing a figure, never `replaceText` on a `.dgm-stage`/`viewBox` string - those are near-identical across figures and the edit lands on the wrong one; slice the figure block by its `<!-- ===== Fn` marker and edit inside it.**

**When an `old_string` spans a boundary, the `new_string` must reproduce every line of it.** Appending a table row by matching `"END\nH1 |4. Application Architecture"` and replacing with `"...\nEND"` silently deletes that H1 - the text leaves no trace of its removal, only a gap in the numbering. Prefer an `old_string` that does not include the following heading; when it must, end the `new_string` with that heading line.

**Never edit `content.txt` prose with an unguarded `run_script` `replaceText`.** `replaceText` returns the input unchanged on a no-match and does not throw, so a silent miss ships a `.docx` whose text contradicts itself. `content.txt` mixes straight (`'`) and typographic (`’`) apostrophes, and hand-typed quotes are the usual cause of the miss. Use `str_replace_edit` (fails loudly), or `grep`/`JSON.stringify` the exact line out of the file first and paste the real bytes. If a batch script must do it, assert each replacement changed the string and throw when it did not.

**Every design lives in `designs/<slug>/`, and NOTHING about a design lives at the project root.** A **change request is not a design** - it lives in `change-requests/<slug>/`, follows the emergency-change template shape (`templates/emergency-change/`), and is a plain Markdown document, never built through the DDD docx pipeline or apm-master.docx. If a document is answering "what do we remove/change in the running environment" rather than "what should we build," it is a change request. Folder: `content.txt` (the DSL source, canonical) · `figures.html` (on the diagram kit) · `figs/*.png` (named for their subject - `credential-pipeline.png`, never `f1.png`) · `output/*.docx` (build artefacts, regenerable) · optional `config/` (policy XML, CSV exports the design defines), `history/` (superseded/pre-standard versions), `research-notes.md`, `transposition-notes.md`. **`designs/README.md` is the register** - doc, version, status, approver, built document, built date - plus the folder convention, the rebuild recipe (`relPrefix`/`imgPrefix`/`idBase` must be unique per document) and the Word-import recipe. Update it in the same change as any version bump. One output format per design (Word); never maintain a parallel HTML copy.

**Importing an authored Word draft:** `templates/detailed-design/authoring/docx-to-dsl.js` converts a `.docx` to the DSL (headings renumbered, bold/highlight, lists, tables with `gridSpan` and `<br>` cells, images as `FIG` lines, cover fields + version history). Always read `r.warnings` (Word comments and tracked deletions do not come across), re-anonymise people to roles by hand, and re-check section cross-references after renumbering. Record what changed in `transposition-notes.md`.

Reference outputs: `APM_Detail_Design_Document_TEMPLATE_Guidance_and_Worked_Example_V1.0.docx` (the exemplar to show people what is expected), `designs/yubikey/output/APM_DDD_YubiKey_Phishing-Resistant_Authentication_V0.1.docx`, and `designs/job-seeker-kiosk/output/APM_DDD_JobSeeker_Kiosk_V1.6.docx` (the current best example: 8 kit figures, 111 cross-refs, consistency + QA + compliance scans clean, 91% policy alignment).

**Inserting a figure mid-sequence renumbers everything after it - in both files.** Adding a new Figure 5 before the existing Figures 5-7 means those become 6-8: update every `FIG|` caption number AND every prose "Figure n" cross-reference in `content.txt`, then re-run `consistency-check.js` (FIGSEQ/FIGREF catch exactly this) before rebuilding. `figures.html` itself doesn't need caption-number edits (captions live in `content.txt`; the kit's `.dgm-cap` shows only the title), but do re-check it if a figure ID or file order matters elsewhere.

**A connector "not joining its shape" is a coordinate bug, not a style one.** If a line's start or end point sits a visible gap away from the box it's meant to touch, the line's `x1/y1` or `x2/y2` simply isn't ON that box's edge - find the box's actual left/right/top/bottom from its `style` attribute and set the coordinate to match exactly (or 2-4px past it, never mid-air). Trust `qa.occlusionScan()` for the overlap-into-the-box case, but verify true near-miss gaps by sampling actual pixel colour at the expected coordinate in the exported PNG (`readImage` + canvas `getImageData`) - eyeballing a downscaled preview image is unreliable at this scale and cost this session several wasted rounds.

**Re-render before re-exporting, every time, no exceptions.** `present_fs_item_for_download` on a figure PNG serves whatever is on disk at that instant - if a `str_replace_edit` to `figures.html` landed after the last `snapshot_element` call, the download is stale even though the source is already fixed. Always sequence: edit -> `show_html` + `get_webview_logs` (qa clean) -> `snapshot_element` -> then export/present. Never reuse an earlier snapshot after a further edit.

**A licence change cascades further than the licence table.** Dropping F5 Security (this session) meant walking: the CA policy inventory (two policies depended on Entra ID P2), the base/admin CA policy list, the §7.3 SOE-alignment narrative, Purview Information Barrier (needs a compliance SKU F3 doesn't carry - re-argued as tenant-separation instead once the tenant was confirmed to hold no corporate data), and every account-creation/rotation runbook description that said "F3 + F5". Grep the whole `content.txt` for the dropped term before declaring the change done, not just the section you were editing.

**A network decision (adding/removing a tunnel, moving an endpoint from private to public) needs an options-assessed decision-register row, not just a settings change.** Write 2-3 alternatives actually considered, the rejection reason for each, and the selected option's rationale in one place (see DR-011 in the kiosk design) - this is what an approver reads first and it prevents the same question being re-litigated in review.

**Third-party or supplied configuration (e.g. a partner's Zscaler tenant export) goes in verbatim in the same order, under a role-neutral attribution** ("provided by the network delivery team") - never invent or infer the individual's name even when the user names them in chat. Large copy-pasted code (a PAC file, a script) renders as one `P` line per source line, not a table cell with `<br>` chains - `docx-builder.js`'s `<br>` splitting only applies inside table cells (`cellP`), not body paragraphs.

**Two working tools live here.** `policies/APM_Policy_Register.html` is the searchable register of every extracted requirement, with per-document impact on our designs and drill-in showing policy clause / design position / options / decision owner. `policies/APM_Compliance_Check.html` checks any dropped document (.docx, PDF, content.txt, text) against `compliance-rules.js` and reports conflicts, gaps, compensating controls already argued, and the remedy for each. The same engine runs headless from `run_script` via `compliance-check.js` - use it to produce a report into `policies/reports/` whenever a design reaches a review milestone. **Run the checker before shipping any design document**, alongside `qa()` and `consistency-check.js`.

**Conditional Access is held as its own register.** `policies/APM_CA_Policy_Analysis.html` carries the tenant export (116 policies: 68 enforced, 43 report-only, 5 disabled) with ten findings and a searchable policy table; `ca-policies.js` is the parsed data, `ca-analysis-data.js` the findings, `ENV-CA` in `environment-config.js` the six advisory interactions. **Three facts every design must respect:** an Entra-joined compliant device satisfies both enforced tenant-wide grants (the MFA-or-device one without any prompt), so blocking is always explicit, never inherited; phishing-resistant and tenant-wide MFA are **report-only**, so they may never be cited as compensating controls; and new CA objects follow the tenant's own `CA-nnn - audience - apps - condition - action` convention, not the Intune schema. The export has no exclusions or conditions column, so exclusion registers cannot be verified from it.

**When adding a compliance rule, give `mustNotSay` rules a context `guard`.** Without one, "DES" matches the Disability Employment Services bookmark, `*.office.com` in a URL allow-list matches the wildcard-certificate ban, and "4-character site code" matches the 14-character password minimum. Test every new rule against a real document and check what it catches by accident - a checker that cries wolf gets ignored. **Character-count rules need adjacency, not proximity** - the credential noun must sit directly either side of the number, with a negative guard for naming context (site code, service tag, hostname, serial, UPN).
