H1 |2. Overview
P |APM delivers Workforce Australia employment services under contract with the Department of Employment and Workplace Relations (DEWR). Job seekers attending APM sites nationally require access to computing facilities for job search, resume preparation, government service interaction, and training. The current device fleet has several problems, including very old hardware, slow internet connections and a lack of manageability.
P |This document defines the detailed design for the Job Seeker Kiosk solution. It replaces the existing shared device model with a standardised architecture: Dell kiosk hardware running Windows 11 Enterprise as a locked-down, multi-app Assigned Access kiosk. Job seekers browse the web directly on the device (Microsoft Edge to the approved job-search, government, support and training sites, and Office for the web). Intune handles device management and policy enforcement; Entra ID in the dedicated apmkiosk.net.au tenant handles identity and access control.
P |Every session is ephemeral. Job seekers work in a locked-down Edge-based kiosk. When a session ends, local session state (browser data, downloads and the user profile) is cleared on the device so the next job seeker gets a clean environment. The design meets Right Fit for Risk (RFFR) accreditation requirements for protecting job-seeker PII.
P |This document covers only the physical kiosk device. The CTA Laptop image and Outreach Laptop will be addressed in separate design documents.

H3 |4.3.2 Idle Sign-Out
B |**Setting Name**: APM-Kiosk-IdleSignOut
B |**Setting Type**: Intune Proactive Remediation / platform script (registers a per-user scheduled task; the idle monitor runs as the interactive user, not SYSTEM)
B |**Scope**: SG-APM-Kiosk-Devices
B |**Setting**: after 10 minutes with no keyboard or mouse input, sign the interactive user out (shutdown /l)
P |Multi-app Assigned Access has no native inactivity sign-out, and existing tools are wrong for this use case: the Windows “Machine inactivity limit” and the screen saver only lock the session. The kiosk therefore must sign the user out on idle, which triggers the User Profile Cleanup wipe (below) and the next-logon OneDrive purge, so every session starts clean.
P |Mechanism: An idle-monitor script reads keyboard/mouse inactivity via the Win32 GetLastInputInfo API and runs as the interactive user through a scheduled task (a logon trigger plus a 60-second repetition). When idle time reaches the 10-minute threshold it calls a sign-out; a 60-second warning is shown first so an active job seeker can dismiss it. This is the control behind user story 05 (auto sign-out after inactivity).
H3 |4.3.3 Logon Lockdown
P |• **Setting Name:** APM-Kiosk-LogonLockdown
P |• **Setting** Type: Intune Proactive Remediation (runs as system)
P |• **Scope**: SG-APM-Kiosk-Devices
P |• **Setting**: Restrict the "Allow log on locally" user right to BUILTIN\Administrators and the device's kiosk user (kiosk-<serial>@apmkiosk.net.au)
P |==The only member of the local Administrators group on a kiosk device is that device's own dedicated support account (4.3.10). The built-in Administrator account is disabled and renamed by the inherited Windows 11 OS baseline, and no privileged-tier (xy or zz) identity is permitted to sign in locally on a kiosk, consistent with the "Deny Local Log On" position in the APM Windows SOE Hardening Standard. A support operator therefore reaches a full desktop only through a non-privileged, device-scoped account, and still cannot install software because App Control is enforced at the device level (4.3.9).==
P |Assigned Access locks the session down but cannot express "deny a session to every other account" - it has no logoff default. Logon Lockdown supplies that: an Intune remediation restricts interactive logon to the assigned kiosk user and local administrators, so any other account is refused at the credential screen. This is prevention by design, and replaces the earlier Shell Launcher logoff-default, which relied on fragile SID matching to rescue the administrator after the fact. The remediation is fail-safe - it never removes Administrators and makes no change if the kiosk user's SID cannot be resolved.

H5 |5.1.1.1.2 Cloud-Only Identity Domain (apmkiosk.net.au)
P |Kiosk identities live in a dedicated cloud-only tenant whose primary domain is apmkiosk.net.au. It is a managed (standard) domain, separate from the APM corporate tenant. It is not federated with ADFS and not synchronised from on-premises Active Directory.
P |apm.net.au is federated to ADFS. For a federated domain, Entra ID hands sign-in to ADFS and expects the account to exist and authenticate on-premises. Two problems follow for kiosk accounts:
P |• Account creation. The kiosk accounts are created in the cloud by the Account Creation runbook through Microsoft Graph. A cloud-created account in a federated domain has no matching on-premises identity, so ADFS cannot authenticate it and the account cannot sign in.
P |• Password rotation. The rotation runbook and the Credential Proxy Function App set and read the account password in the cloud. A federated domain delegates password validation to ADFS, so a cloud-set password fails. Rotation cannot then drive the kiosk sign-in.
P |A managed domain removes both problems. Entra ID authenticates apmkiosk.net.au accounts directly, with no ADFS or on-premises dependency. The runbook creates each account, then sets and rotates its passphrase through Graph. The device signs in with that passphrase to Windows on the kiosk. Password expiration is disabled on the account, and rotation is driven only by the runbook.
P |The domain carries kiosk service identities only. No human users, no mailboxes and no mail flow. Email handling and ongoing management for the domain are set out in the Domain Management section.
H5 |5.1.1.1.3 Account Creation
P |Each kiosk device has its own Microsoft 365 F3 account. The account is created automatically by an Azure Automation Runbook when the device first joins the dynamic security group SG-APM-Autopilot-Kiosk-Devices on Entra ID-join completion.

H5 |5.1.1.1.8 Lock Screen Image Generation
P |The Credential Proxy renders the per-device lock-screen PNG server-side (showing the device UPN and current passphrase), so no password is exposed to the device as text. H5 |5.1.1.1.9 Rotation Schedule
P |Kiosk credentials are managed using a per-device credential model. Each kiosk device has a unique Entra ID account and password, stored as a per-device secret in Azure Key Vault. Password rotation is performed individually for each kiosk account by an Azure Automation Runbook running in the Azure Automation sandbox under the Automation Account managed identity.
P |The password rotation Runbook iterates through the kiosk user accounts in scope, generates a new ANIMAL-noun passphrase for each device, updates it in Entra ID, writes the updated secret to Azure Key Vault, and logs the event to Azure Log Analytics. Rotation runs on a 12-month schedule and on demand for operational or security need.
P |Each kiosk device retrieves its per-device lock-screen image through the Credential Proxy Azure Function App, which renders it server-side showing the device-specific sign-in credentials. The Intune Proactive Remediation detects a credential change by comparing a local version marker (version.txt) with the current secret version reported by the proxy, and where they differ it fetches and applies the newly rendered lock-screen image.
P |The lock screen image is rendered server-side by the Credential Proxy and fetched to C:\APM\Kiosk\lockscreen.png, with a local version marker in C:\APM\Kiosk\version.txt recording the applied secret version. This keeps the displayed credentials aligned to the device's currently assigned password.

H2 |5.3 Network & Infrastructure
P |The Jobseeker kiosk solution reuses the existing Job Seeker network to securely support walk-in participants accessing online job services directly via Microsoft Edge on the kiosk device.
P |Kiosk devices are connected to the existing Job Seeker VLAN, which will be repurposed for kiosk use and renamed to APM-KIOSK. This is not a new network deployment; rather, the existing wireless service is being updated to support the kiosk solution, including an increase to 20Mbps bandwidth per site and the removal of the existing CAPTCHA requirement to allow a smoother kiosk user experience. The APM-KIOSK SSID will not be publicly visible, and access to it will be controlled through a pre-shared key deployed to kiosk devices via Intune policy. The network remains tightly controlled and restricted to the connectivity required to support the APM Azure tenant, Microsoft endpoints, and other approved service dependencies, including Azure Key Vault and Azure Function App.
P |The design uses the organisation’s existing public internet breakout, complemented by the renamed APM-KIOSK SSID. Job-seeker web traffic and Microsoft 365 endpoints are reached directly from the kiosk VLAN via Zscaler. The credential-pipeline Azure resources (Key Vault, Credential Proxy Function App, Automation) live in the apmkiosk.net.au tenant subscription.
P |As part of this design, the existing Job Seeker VLAN is dedicated exclusively to kiosk devices and does not permit personal mobile internet connectivity or personal device access. The capability for personal devices to connect to this network will be removed. Should a user require internet access, they can use a kiosk device. All kiosk endpoints will connect solely to the renamed APM-KIOSK network, ensuring controlled access and appropriate separation from standard corporate and personal connectivity use cases.
P |The solution does not provide general access to APM corporate systems, internal business applications, or unrestricted internet services. All permitted traffic is subject to inspection and policy enforcement through APM-managed network security controls, including Palo Alto east-west firewalls and approved egress paths to internet and Zscaler. All other traffic is blocked.

H2 |6.4 OneDrive Session Purge
P |Each kiosk account's own OneDrive for Business is enabled as ephemeral scratch storage so Office for the Web can create and edit documents; the SharePoint/OneDrive service plan (SHAREPOINTDESKLESS) is enabled on the F3 licence for this purpose. Because Office for the Web autosaves continuously and cannot be turned off, a job seeker's document is present in that OneDrive during the session; three layered controls then guarantee that no job-seeker file survives between sessions. All three permanently delete items (bypassing the 93-day OneDrive recycle bin) and all three are fail-safe by design. Figure 6 places the three layers on the session timeline.
FIG|onedrive-purge.png|Figure 6. OneDrive session purge - three layers across the session timeline|1520|1080
H3 |6.4.1 Logon Purge (Primary)
P |A scheduled task (APM-Kiosk-OneDrive-Purge) runs Clear-KioskOneDrive.ps1 as the interactive user at every logon. It acquires a delegated Microsoft Graph token through the WAM broker with the scope Files.ReadWrite - a delegated grant, so it can only ever touch the signed-in account's own drive - and permanently deletes every top-level OneDrive item. Because it fires at logon, every session begins with a clean drive regardless of how the previous session ended; this is the reliable layer, since a logoff script never runs after a hard power-off. The task is registered once per device (as system) by an Intune platform script, Register-KioskOneDrivePurge.ps1, and the payload is delivered as a Win32 app. Any token or purge error is logged and the script exits 0, so it can never block logon.
H3 |6.4.2 Logoff Purge (Secondary)
P |The same scheduled task also fires on user-initiated logoff (Security event 4647), running the identical purge as the session tears down. Authentication during sign-out is fragile, so this layer is best-effort - it complements the logon purge rather than replacing it.
H3 |6.4.3 Nightly Fleet-Wide Purge (Tertiary)
P |An Azure Automation runbook, Clear-AllKioskOneDrive.ps1, runs nightly as a fleet-wide catch-all. Using app-only Microsoft Graph via the Automation managed identity (the application permission Files.ReadWrite.All, which in the dedicated apmkiosk.net.au tenant can only reach kiosk drives because the directory holds no other identities productivity identities), it enumerates SG-APM-Kiosk-Users and permanently deletes each account's top-level OneDrive items. It catches any device that never ran its own logon or logoff purge - a hard power-off, an extended offline period, or a disabled task. The runbook touches no Key Vault, so it runs in the Azure Automation sandbox like the other credential-pipeline runbooks. It is scheduled nightly at approximately 02:00, before the 03:00 patch and restart window. Per-user isolation means one account's failure is logged and the batch continues; accounts with no provisioned OneDrive are skipped, so under the default OneDrive-suppressed posture the runbook is a safe no-op.
P |The two device-side layers use a delegated grant (own drive only); the runbook uses an app-only grant that the dedicated tenant confines to kiosk drives. All three use the Graph permanentDelete operation so purged content bypasses the recycle bin and cannot be recovered by the kiosk account.
H2 |6.5 Office for the Web Storage Model
P |Word, Excel and PowerPoint on the web are cloud-storage-backed applications so they edit a document in place in OneDrive for Business or SharePoint Online, and their AutoSave writes every change to that store continuously and cannot be turned off (per the Microsoft Office for the Web service description). There is no browser-only editing mode that keeps a document off the cloud, so a store is a prerequisite for document creation - without one, the web apps are view-only and cannot create or edit a resume.
P |User story 08 requires job seekers to create resumes and documents in Microsoft Office on the kiosk. To meet it, each kiosk account's own OneDrive for Business (2 GB under the F3 licence) is enabled as ephemeral scratch storage - Posture B. The alternative, suppressing OneDrive entirely (Posture A), would guarantee that nothing is ever written to OneDrive but would reduce the web apps to view-only and fail the resume-creation requirement, and was rejected for that reason.
P |Because AutoSave cannot be disabled, a job seeker's document is present in the kiosk account's OneDrive for the duration of the session. The design does not attempt to prevent this; it prevents persistence between job seekers. The three-layer OneDrive Session Purge (section 6.4) is the enforcing control: the logon purge guarantees every session starts with an empty drive, and the logoff and nightly-runbook layers are catch-alls; all three permanently delete content, bypassing the 93-day recycle bin. The guarantee the design makes is therefore that no job-seeker file persists between sessions - not that nothing is written to OneDrive during a session.
P |The only store any kiosk identity can reach is its own OneDrive. The kiosk fleet is in the dedicated apmkiosk.net.au tenant, which holds no corporate content, and the Purview Information Barrier and Conditional Access confine kiosk accounts to their own OneDrive as the Office-for-the-Web storage layer (section 7). Corporate SharePoint and OneDrive for Business are not reachable from a kiosk.

H3 |7.2.6 Microsoft Office Hardening
P |As Microsoft Office is available online only, the organisation acknowledges that Microsoft Word, Excel, and PowerPoint Online do not support endpoint-level application hardening controls such as macro configuration, Protected View enforcement, OLE/DDE restrictions, or application allow-listing. This limitation is inherent to Microsoft’s SaaS delivery model and cannot be mitigated through Intune or endpoint configuration. In the Job Seeker Kiosk environment, this risk is accepted on the basis that kiosk devices are single-purpose, locked-down endpoints with restricted user interaction, hardened browser configuration, enforced device compliance, and ephemeral user sessions that do not persist data locally. Access to Microsoft 365 services is constrained through Conditional Access, network and device trust controls, and Microsoft-managed service security, rather than individual user authentication factors such as MFA, which are not appropriate for anonymous or assisted kiosk use.
H3 |7.2.7 Information Barrier
P |APM kiosk users in the dedicated apmkiosk.net.au tenant retain full use of the Office for the Web applications (Word, Excel and PowerPoint in the browser), including the ability to create and edit their own documents in OneDrive. Because the kiosk fleet is in a separate, dedicated tenant, there are no APM corporate SharePoint sites present for kiosk users to reach; the Information Barrier below is retained as defence-in-depth.
P |A conventional Conditional Access block against the SharePoint Online service is deliberately **not** used here. Office for the Web, Teams and Office.com all depend on the SharePoint Online service, and OneDrive shares that same service and Conditional Access application - there is no separate OneDrive app to target. Blocking at the service level would therefore disable the very web apps and OneDrive editing the kiosk role relies on; the control cannot be drawn where it is needed.
P |Instead, we implement Microsoft Purview Information Barriers. The kiosk users are placed in a dedicated segment, and a block policy isolates that segment from all others. Information Barriers operates at the site and segment level rather than the service level, so kiosk users are denied access to corporate SharePoint sites while their own OneDrive - and therefore the Office web applications - continues to function normally.

B |Purchase apmkiosk.net.au through APM’s existing GoDaddy account, in line with current domain practice.
B |.net.au requires an eligible Australian presence. Register in APM’s legal entity with a matching ABN. Keep registrant, admin and technical contacts on APM-controlled mailboxes, not personal accounts.
B |Enable auto-renew and registrar lock. A lapsed kiosk domain breaks sign-in and password rotation across the whole fleet.
B |Record the domain in the APM asset register and CMDB with Cyber Security as owner.
H3 |9.4.2 Establish the apmkiosk.net.au Tenant
B |apmkiosk.net.au is the primary domain of a NEW dedicated Microsoft 365 tenant. Verify it in that tenant with the TXT record Microsoft provides.
B |Do not federate the domain and do not include it in Entra Connect sync scope. It must stay cloud-only. This is the control that lets the runbook create accounts and rotate passwords.
B |The tenant default domain is its .onmicrosoft.com; apmkiosk.net.au is verified as the primary domain for kiosk UPNs. There is no apm.net.au in this tenant.
H3 |9.4.3 Block Email on the Domain
P |The domain sends and receives no mail. Two layers enforce this:
B |Licence layer: the F3 default-deny model leaves Exchange Online disabled on kiosk accounts, so no mailbox is provisioned.
B |Domain layer: publish the anti-spoof DNS records below and add an Exchange Online mail flow rule that rejects any message sent to or from *@apmkiosk.net.au.
P |Do not publish an MX record that points to Exchange Online. Publish a null MX to state the domain accepts no mail.
H3 |9.4.4 Anti-Spoofing DNS (SPF, DMARC, DKIM)
P |Even with no mailboxes, the domain name can be spoofed. Publish records that tell receivers no mail from apmkiosk.net.au is legitimate.
B |SPF: v=spf1 -all. States that no server is authorised to send from the domain.
B |DMARC: v=DMARC1; p=reject; at host _dmarc. Tells receivers to reject anything claiming to be from the domain.
B |DKIM: Microsoft advises against DKIM for a non-mailing domain, as it signs mail that will never be sent. DKIM is documented below as optional and deferred. If a future workflow needs to send from the domain, enable DKIM then and move DMARC through p=none and p=quarantine before p=reject.
B |Null MX: publish 0 . to signal no mail acceptance (RFC 7505). If GoDaddy will not accept a null MX, publish no MX record at all.
B |Add matching SPF and DMARC records for the tenant onmicrosoft.com domain if they are not already present.

H3 |9.4.5 Device enrolment DNS (Intune / MDM Autodiscovery)
P |Two CNAME records published on apmkiosk.net.au let Windows devices discover the Intune enrolment and Microsoft Entra device-registration endpoints from the kiosk UPN suffix. They are added to the DNS provider alongside the anti-spoofing records above. The domain must already be verified in the tenant (the Entra verification TXT, section 9.4.2) before enrolment will work.
B |CNAME enterpriseregistration.apmkiosk.net.au > enterpriseregistration.windows.net (TTL 1 hour). Microsoft Entra ID device-registration autodiscovery (device registration/Workplace Join).
B |CNAME enterpriseenrollment.apmkiosk.net.au > enterpriseenrollment-s.manage.microsoft.com (TTL 1 hour). Intune MDM enrolment autodiscovery points the device at the Intune enrolment service from the UPN domain.
H3 |9.4.6 Firewall, Gateway and Filtering Impact
P |The kiosk domain is an identity namespace, not a new network destination. Sign-in traffic still goes to the Microsoft endpoints already allowed for the solution, such as login.microsoftonline.com. No new outbound firewall rule is needed for authentication. Check and, where needed, adjust:
B |Zscaler and web filtering: no new destinations, but confirm no rule blocks the new UPN suffix during SSO or URL inspection. If any proxy rule keys on the apm.net.au user identity, extend it to apmkiosk.net.au.
B |Credential Proxy Function App and Key Vault: unchanged. Both are keyed to the device serial, not the domain, and are reached over their public endpoints with Entra ID authentication and Azure RBAC. No firewall change.
B |Inbound mail gateway or connector: if APM runs one, add apmkiosk.net.au to its reject or non-routable list so it does not attempt delivery.
B |SIEM and Sentinel: extend any sign-in or identity detection that filters on apm.net.au to include apmkiosk.net.au, so kiosk sign-ins and failures are captured.
B |Certificate and UPN suffix references: confirm no gateway, VPN or device policy pins the apm.net.au UPN suffix in a way that would exclude kiosk accounts.
H3 |9.4.7 Maintenance and Monitoring
P |• Domain expiry: monitor renewal. A lapse breaks fleet sign-in. Check quarterly and alert 60 days out. Owner: Cyber Security.
P |• DNS records: review SPF, DMARC, DKIM (if enabled) and MX at each design review and after any tenant email change.
P |• DMARC reports: if an rua address is set, review aggregate reports for spoof attempts. Optional given the domain sends no legitimate mail.
P |• Domain verification TXT: safe to leave in place after verification. Do not remove records that ongoing controls depend on.
P |• Add the domain and its controls to the annual RFFR and ISMS review so they stay documented.
H3 |9.4.8 Operational Overhead Summary
P |The net business impact is modest: one extra domain to renew and monitor, a handful of DNS records to maintain and monitoring scope extended to a second UPN suffix. The alternative, forcing kiosk accounts onto the federated apm.net.au domain, would need ongoing on-premises AD account management and manual password handling for every device. That removes the automation this design relies on.
