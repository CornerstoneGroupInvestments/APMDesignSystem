APM Digital Workplace — Job Seeker Kiosk (Interim Thick-Client Solution)

Conditional Access Policy Set

Version 0.1 draft  •  20 July 2026  •  Prepared by the Twiki Corp project team

Passwordless-MFA exempt design — compensating controls

Purpose

The interim kiosk solution signs in with fixed per-device usernames and passwords, so kiosk identities cannot satisfy multi-factor authentication. This policy set removes MFA for the kiosk population only and replaces it with layered compensating controls: access is bound to known, compliant, Entra-joined kiosk hardware, at APM sites, on approved applications only, with every credential-theft pathway (legacy auth, device-code phishing, off-site replay) explicitly blocked.

All policies target the kiosk user group SG-APM-Kiosk-PlanB-Users. Device conditions use a device extension attribute (extensionAttribute1 = "KioskPlanB") stamped on kiosk device objects, because Conditional Access device filters cannot reference an Entra security group. The device group SG-APM-Kiosk-PlanB-Devices continues to drive Intune policy assignment. APM sites do not present dedicated egress IP ranges, so no location-based policy is used; device binding (policies 1 and 2) carries the compensating role a trusted-location control would otherwise provide.

Deployment note: build every policy in report-only mode first, confirm expected sign-in outcomes in the Entra sign-in logs, then enable. Exclude the kiosk user group from any tenant-wide MFA policy, and exclude the break-glass accounts from all policies below, per APM CA standards.

Policies

1  CA-APM-KioskPB-RequireCompliantDevice

Grant — require compliant, Entra-joined kiosk device

Allows kiosk sign-in only from devices that are Entra ID joined, carry the kiosk device attribute, and are marked compliant by Intune. A valid username and password is useless on any other machine: the sign-in cannot present a compliant kiosk device claim. Session controls stop tokens outliving the working day and prevent the browser keeping the user signed in after the session ends.

UsersInclude SG-APM-Kiosk-PlanB-Users
ResourcesAll resources
ConditionsPlatforms: Windows. Device filter (include): device.trustType -eq "AzureAD" -and device.extensionAttribute1 -eq "KioskPlanB"
GrantRequire device to be marked as compliant
SessionSign-in frequency 12 hours; persistent browser session: never persistent

2  CA-APM-KioskPB-BlockNonKioskDevices

Block — deny all non-kiosk devices

The explicit deny that closes the gap left by policy 1: it blocks kiosk identities on every device that is not a tagged kiosk — including unregistered and unknown devices, which present no attribute at all and therefore match the filter. Together, policies 1 and 2 hard-bind each kiosk identity to APM kiosk hardware.

UsersInclude SG-APM-Kiosk-PlanB-Users
ResourcesAll resources
ConditionsDevice filter (include): device.extensionAttribute1 -ne "KioskPlanB"
GrantBlock access

3  CA-APM-KioskPB-BlockNonWindows

Block — deny non-Windows platforms

Backstop to policy 2: denies kiosk sign-ins from Android, iOS, macOS and Linux outright. Platform detection is evaluated independently of device filters, so a spoofed or anomalous device record still fails on platform.

UsersInclude SG-APM-Kiosk-PlanB-Users
ResourcesAll resources
ConditionsPlatforms (include): Android, iOS, macOS, Linux
GrantBlock access

4  CA-APM-KioskPB-BlockLegacyAuth

Block — legacy authentication

Legacy protocols (IMAP, POP, SMTP AUTH, Exchange ActiveSync) do not carry device claims, so they bypass every device-based control above. For password-only accounts this is the classic attack path; it is closed unconditionally.

UsersInclude SG-APM-Kiosk-PlanB-Users
ResourcesAll resources
ConditionsClient apps: Exchange ActiveSync clients, Other clients
GrantBlock access

5  CA-APM-KioskPB-BlockAuthFlows

Block — device code flow and authentication transfer

Device-code phishing is the leading technique for stealing sessions from fixed-credential accounts: the attacker initiates a device-code sign-in and lures the user (or an automated kiosk flow) into approving it elsewhere. Authentication transfer similarly moves a session to an attacker-controlled device. Neither flow has any legitimate use on a kiosk.

UsersInclude SG-APM-Kiosk-PlanB-Users
ResourcesAll resources
ConditionsAuthentication flows: device code flow, authentication transfer
GrantBlock access

6  CA-APM-KioskPB-BlockRiskySignIn

Block — sign-in risk medium and above

Identity Protection blocks anomalous sign-ins (impossible travel, anonymised IP, token anomalies) at medium or high risk. The tenant standard remediates risk with MFA; kiosk accounts can never satisfy that, so the kiosk policy blocks outright and at a lower threshold. Requires Entra ID P2 coverage for the kiosk identities — confirm licensing position with SoftwareOne.

UsersInclude SG-APM-Kiosk-PlanB-Users
ResourcesAll resources
ConditionsSign-in risk: medium, high
GrantBlock access

7  CA-APM-KioskPB-BlockUnapprovedApps

Block — default-deny all applications except the resume surface

Kiosk identities exist for one task: creating and editing resumes in Office for the web. This policy blocks every cloud application by default and excludes only the services that task requires — Office for the web and SharePoint Online (OneDrive authenticates as SharePoint Online; it is required for Office web sessions and for staging USB files). Exchange, Teams and all other workloads are denied by default rather than by individual block policies. Data-plane exposure created by allowing SharePoint/OneDrive is controlled by Purview Information Barriers and the scratch-OneDrive wipe process, documented in the DDD §7.2.

UsersInclude SG-APM-Kiosk-PlanB-Users
ResourcesInclude all resources; exclude Microsoft Office Online, Office 365 SharePoint Online (add Office 365 portal only if report-only testing shows the sign-in entry flow requires it)
GrantBlock access

How the policies work together

No single policy carries the design. Each policy addresses a distinct control layer, and access is granted only where every layer is satisfied concurrently: approved hardware, a modern authentication client, approved applications, and normal sign-in behaviour.

Supporting controls outside Conditional Access

  • Security-info registration block — kiosk accounts must be prevented from registering MFA/SSPR methods, so an attacker holding the password cannot enrol their own authenticator.
  • Tenant MFA exclusions — exclude SG-APM-Kiosk-PlanB-Users from tenant-wide MFA policies; verify no "all users" policy demands a control these accounts cannot meet.
  • Credential hygiene — Key Vault-managed per-device passwords with scheduled rotation; Entra smart lockout and banned-password list apply.
  • Data plane — Purview Information Barriers isolate the kiosk segment from all staff content in SharePoint and OneDrive; scratch OneDrive wiped at logoff plus scheduled sweep.
  • Device plane — Assigned Access single-app lockdown (Edge + Zscaler + File Explorer), Intune compliance policy, BitLocker, and Zscaler client for web filtering.
