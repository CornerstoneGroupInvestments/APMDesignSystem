APM-PK-03 · Configuration procedure · V1.0

ES Participant Kiosk
Windows Autopatch Configuration

For APM Digital Operations and the APM Solution Engineer · APM Standard Operating Environment Program

Registers the Participant Kiosk fleet with Windows Autopatch and configures the two update-behaviour objects Autopatch does not own. Done once for the fleet, not per device. Allow half a day, most of which is waiting for registration to report.

Four things to know before you start

  1. Autopatch owns the update policies, so do not create update rings. Registration hands quality, feature, driver, firmware and Microsoft Edge updates to Autopatch, and it creates and maintains its own underlying Intune policies to deliver them. A hand-made update-ring policy assigned to this fleet fights those and is the usual cause of a device that reports compliant and never patches.
  2. The kiosks need their own Autopatch group, and they must leave the estate one first. A device can belong to only one Autopatch group. The estate already patches through APM-Autopatch-*, so step 1 excludes the kiosks from its source group before step 2 creates theirs. Skip step 1 and the fleet reports Not ready or Not registered rather than patching.
  3. You do not hand-create the three ring groups. Autopatch creates and owns an Entra group per deployment ring and names it after the ring. Create the Autopatch group Kiosk-Autopatch with rings Test, Ring1 and Ring2, and the three groups named in the request appear on their own. Hand-built groups of the same name would sit beside the real ones and confuse every later assignment.
  4. The 30/70 split is Autopatch's, not an Entra rule. Entra dynamic membership has no percentage operator. Autopatch dynamic distribution does, so the split is set on the ring and the service allocates devices to satisfy it.
  5. Two objects stay yours. Autopatch decides which update and when it is offered. It does not set what the device does at install time, and it does not manage Delivery Optimization. Those are steps 6 and 7 and they are ordinary Intune profiles.
  6. Two of the settings exist because nobody is standing at the device. A kiosk has no signed-in person to defer an update or dismiss a restart prompt, and the screen faces the public. Pause and check are disabled and notifications are turned off for that reason, not for tidiness.

Step 1 · Carve the kiosks out of the estate Autopatch group

Entra admin centre › Groups › the source group behind the existing APM-Autopatch rings

The estate already runs an Autopatch group with rings APM-Autopatch-Test, APM-Autopatch-Ring1 at 30% and APM-Autopatch-Ring2 at 70%, fed by dynamic group distribution. A device can belong to only one Autopatch group. If its source group resolves all Windows devices, every kiosk is already in it, and creating a second Autopatch group over the same devices puts them in both.

Do this before step 2, not after. A device caught in two Autopatch groups reports Not ready until someone picks a group for it, and an overlap that exists before registration leaves the device Not registered and unpatched. Fixing 540 of those by hand afterwards is the failure this step exists to avoid.

  1. Open the Entra group the estate Autopatch group uses for dynamic distribution
  2. Add an exclusion for the kiosks to its membership rule. Against a rule that currently reads (device.deviceOSType -eq "Windows") or similar, append:
    -and -not (device.displayName -startsWith "APM-PK-")
  3. Save and wait for the rule to re-evaluate. Confirm the kiosk count in that group falls to zero
  4. If any kiosk has already registered under the estate group, check Windows Autopatch › Autopatch groups › Membership and confirm it has left before continuing
Why exclusion and not a separate estate ruleThe kiosk fleet is already defined by one condition, the APM-PK- name prefix, and that same condition drives every configuration profile, application and compliance policy it receives. Reusing it here means there is one definition of what a kiosk is, in one place. A hand-maintained exclusion list would be a second definition that drifts.

Step 2 · Create the kiosk Autopatch group

Intune admin centre › Tenant administration › Windows Autopatch › Autopatch groups › Create

One custom Autopatch group covers the whole fleet. Creating it registers the devices and builds the rings in the same action, so there is no separate registration step.

  1. Name the Autopatch group Kiosk-Autopatch. Get this exactly right: Autopatch names each ring group <Autopatch group> - <ring>, so this name is what produces the three group names in the request. A typo here is a typo in all three
  2. Add the Entra group sg-dyn-dvc-cdg-participant-kiosk as the source group. Every device it contains is registered with Autopatch and becomes available for distribution
  3. Test and Last are already there. Every Autopatch group starts with those two, and neither can be renamed or removed. You are adding rings between them, not building all four
  4. Select Add deployment ring twice. Each added ring arrives with a sequential placeholder name such as Deployment ring 3. Type over it: name them Ring1 and Ring2. The ring name is what names the Entra group, so the placeholder is what you would be stuck with
If the placeholder reads Deployment ring 4 or higher, you are in the wrong place. The number continues from the rings already in the group you have open, so a high number means you are editing the estate APM-Autopatch group rather than creating a new one. Cancel, go back to Autopatch groups, and use Create. Adding kiosk rings to the estate group patches the whole estate on kiosk timings.

Step 3 · Set the ring distribution

Deployment ring composition page, during the same create wizard

Ring1Dynamic30%~159

  1. Set Test to Assigned distribution and point it at sg-stc-dvc-cdg-participant-kiosk-Autopatch-Test. Test does not support Dynamic distribution, so it takes no percentage and sits outside the split
  2. Leave Last with no group assigned. It is Assigned-only as well, so with nothing assigned it stays empty and takes no devices
  3. Set Ring1 and Ring2 to Dynamic distribution against the source group from step 1
  4. Enter 30 and 70. The percentages must total exactly 100 or the page will not accept them. Do not use Apply default dynamic group distribution, which overwrites both with the Microsoft defaults
  5. Complete the wizard: update types, deployment settings, release schedules
Why 30/70 and not an Entra ruleEntra dynamic membership has no percentage operator, so a split like this cannot be expressed as a membership query. Autopatch dynamic distribution is the only mechanism that does it, which is why the rings are built here and not in Entra. It also means the allocation is Autopatch's to calculate: you set the shape, the service picks the devices.
An Assigned ring takes exactly one Entra group, and that is a reason to keep the two Autopatch groups apart, not a reason to merge them. The estate APM-Autopatch - Test already holds its one group, so there is no slot to add the kiosks into. Do not replace what is there, and do not nest the kiosk group inside it. Kiosk-Autopatch has its own Test ring with its own empty slot, which is where sg-stc-dvc-cdg-participant-kiosk-Autopatch-Test goes. If you are looking at a Test ring that already has a group in it, you are in the estate Autopatch group rather than the kiosk one.
A Test device cannot be double-countedThe Test devices are also in the source group, so they are eligible for the percentage split as well. Autopatch resolves this in the right direction: within one Autopatch group, Assigned distribution takes precedence over Dynamic. A device in sg-stc-dvc-cdg-participant-kiosk-Autopatch-Test lands in Test and nowhere else, so no exclusion is needed.
Know what the split is and is notAutopatch allocates across Ring1 and Ring2 by count, not by location, so both rings hold devices drawn from sites across the country. That is useful, because a fault reaches 30% of sites rather than 30% of one region. It also means the split cannot be read as "these sites first", and a site with five kiosks will usually have devices in both rings. If a particular site must patch as a unit, that is an Assigned ring, not a percentage.

Step 4 · Confirm the registration ran

Windows Autopatch › Devices, and Autopatch groups › Membership

  1. Devices read Registered. A device that fails readiness appears under Not registered with a reason
  2. Open the Autopatch group membership view and confirm the Ring1 and Ring2 counts sit near 30 and 70 per cent of the registered total. Early in the rollout, with few devices registered, the ratio will be coarse and settles as the fleet grows
  3. Confirm every Test device appears in Test and in neither Ring1 nor Ring2

Step 5 · Confirm what Autopatch has taken over

Check that no hand-made update policy is still assigned to the fleet.

  1. Intune admin centre › Devices › Windows › Update rings for Windows 10 and later
  2. Confirm that no ring targets sg-dyn-dvc-cdg-participant-kiosk. Policies whose name begins Windows Autopatch are Autopatch's own and are left alone
  3. Devices › Windows › Feature updates and Quality updates: same check
Edge is not an Intune application on this fleetAutopatch updates Microsoft Edge and the operating system. Only LibreOffice, Zscaler, TeamViewer and the kiosk's own packages are Intune applications. If someone adds Edge as a Win32 application later, it will fight Autopatch for the same binary.

03:00 is a backstop, not the usual pathA kiosk restarts every ten minutes of inactivity, and the restart is a real restart because the session cleanup remediation sets HiberbootEnabled = 0 and turns fast startup off. Most updates therefore finish on an idle restart during the day. The 03:00 window exists for the update that needs a restart the device has not happened to take, and for a site that leaves a device switched on and in use all day.
