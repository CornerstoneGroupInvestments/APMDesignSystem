# Participant Kiosk - runbooks

Supplier-facing and operational procedures for the ES Participant Kiosk solution. Written from `../content-technical.txt` (TCD V1.8) and `../config/intune-object-register.md`, never from the superseded `uploads/CN-JSK-*` set.

**Two formats, one source.** The HTML is authored and canonical - it is the version to edit, and it prints straight to PDF. The Word document is a build artefact for circulation and mark-up:

```
runbooks/
  CN-PK-01-Participant-Kiosk-Build-Procedure.html   authored, canonical
  content-cn-pk-01.txt                              DSL, generated from the HTML
  output/APM_CN-PK-01_...V1.0.docx                  built on apm-master.docx
```

Rebuild after any change to the HTML. The DSL is regenerated by conversion, never hand-edited, or the two formats diverge:

1. Walk the HTML and emit DSL - `h2`&rarr;`H1`, `h3`&rarr;`H2` (the `.time` badge appended to its heading in brackets), `p`&rarr;`P`, `ol`&rarr;`NUM`, `ul`&rarr;`B`, `table`&rarr;`TBL`/`TH`/`TR`/`END`, and the `.stop` / `.see` / `.tbc` blocks to a `P` keeping their bold label. `.cmd` blocks become `Type: <command>   then press Enter`, since the DSL has no monospace run.
2. Set column widths by hand afterwards. Equal widths are unreadable for a tick sheet or a register - the record sheet is `900,1200,7260`, open items `700,1500,7160`, two-column tables `2900,6460`.
3. Build on `templates/detailed-design/authoring/apm-master.docx`, the generic APM cover set, not one of the three design-tier masters. Reserved build values: `rCN`/`cnpkFig`/`7100`.
4. Assert the output: 33 headings, all cover fields present, no forbidden brand or personal name, no em dash, no section symbol.

Headings carry no section numbers, deliberately. The stages already number themselves, and a second numbering ("6. Stage 2 - Firmware verification") reads as a contradiction. Word builds its Contents from the heading styles either way.

## What CN-PK-01 is built on

Nine stages in build order, with a printable per-device build record sheet. It carries no reference to any previous procedure or design. Facts taken from the design, each with one home:

- **The APM image is installed from USB at Stage 3, before Autopilot** - it carries the required Windows version, current updates and APM certificates, and replaces the factory operating system. Autopilot provisions on top of it and does not change the Windows version. The internal drive is always erased and reimaged, which is why four rebuild paths route back to Stage 3.
- **One build USB drive, prepared once** - APM emails a download link for `Windows11_25H2_PK_Updated_20260827.iso` alongside the scripts. The image is written to the drive with Rufus, **FAT32** with GPT and UEFI (non CSM), then the three script files are copied to its top level. FAT32 is not a preference: NTFS media boots through Rufus's own UEFI:NTFS loader, which Secure Boot commonly refuses, and Stage 2 requires Secure Boot enabled. FAT32 keeps both requirements satisfiable and the drive writable. The drive stays connected from Stage 3 into Stage 4, because Stage 4 runs the scripts on it. There is no second drive.
- **The date in the image filename is the version.** A technician confirms the filename against the most recent APM email before starting a batch. Stage 3 erases the internal drive, so a stale image costs a full rebuild.

- **Group tag `PARTICIPANT`** - `sg-dyn-dvc-cdg-participant-kiosk-autopilot` keys on `device.devicePhysicalIds -any (_ -eq "[OrderID]:PARTICIPANT")`. A wrong tag means no Autopilot profile, so the device builds into a plain desktop. Verified at 4.2, with the correction click path.
- **Userless enrolment status = Allowed** - TCD DEP-004. Reads Blocked on any device that has completed a self-deploying build before, which is every rebuild and every returned device. Checked before Stage 7 and before any rebuild, not after the failure.
- **TPM 2.0 attestation reachability** - TCD 4.6.2 step 12. Self-deploying attests the TPM, so the four addresses are a build facility network precondition. Named, with the `0x800705B4` symptom that means they are blocked.
- **ESP blocks device use until LibreOffice, Zscaler Client Connector and TeamViewer install** - so the 20 to 60 minute wait is expected behaviour, not a stall, and 90 minutes is the escalation line.
- **Validation set** - the restricted session, the Assigned Access application list (Edge, LibreOffice Writer, Calc and Impress, File Explorer under its namespace restriction), the Edge managed favourites, the Zscaler Client Connector, and the restart session purge. LibreOffice launch is called out as the most common single fault, per `../research-libreoffice-kiosk.md`.
- **`APM-PK-` device name prefix** - the second dynamic group keys on it, so a name without it is the same defect as a wrong tag and gets the same treatment: rebuild.

## Register

Written for a build technician: every keystroke, every click path, `[Enter]` marked at each carriage return, and a "Report to APM if" block wherever proceeding forfeits a provisioning run. Engineer register throughout, not conversational - Microsoft's own terms for what is on screen (restricted user experience, Enrolment Status Page, managed favourites, attestation), the imperative for instructions, and no second-person commentary. No individual is named anywhere in it: the two batch files are referred to by filename only.

**Contrast, on any printable artefact.** Run a WCAG AA pass over the whole page before shipping, the same as a design figure set. Two traps this document hit:

- **A running footer inherits nothing.** The confidentiality marking was `#7B87AD` on white at 8.5pt, 3.26:1. A commercial-in-confidence marking has to be legible, so footers take `#41507F`.
- **A unicode checkbox glyph is text, and it prints thin.** `&#9744;` at 14pt was 3.26:1 and below the 24px large-text threshold, so 3:1 did not apply. Replaced with a real bordered square (`13pt`, `1.5pt solid #1F2D58`), which is both compliant and darker on paper. Use the bordered square on any printed build record sheet.

`#7B87AD` is fine as a decorative border (the `.see` block's left rule) where the 3:1 non-text threshold applies. Scope a contrast guard to `color:` declarations so it does not flag those.

**Two terms that are not interchangeable.** *Purge* is the per-restart clear of participant session data, which is what Test 7 proves. *Wipe* is erasing the disk for a rebuild. Test 7 read "the wipe is not working", which named the wrong control in the one test that exists to prove it.

**When a choice is removed, every clause that presupposed it has to go too.** Deleting Method A left 4.2 opening `Irrespective of who performed the import`, which implies a second performer that no longer exists. Grep for the removed concept, not just the removed heading.

**A register pass has to cover table cells and column headings, not just prose.** Three rounds of review found the same defect: block text and headings rewritten, table content left in the original voice. Tables are where a technician actually works, so they carry the register the reader judges the document by.

**Do the pass mechanically, not by reading.** Reading section by section structurally cannot catch a scattered pronoun or a single stale column heading, which is why it failed three times. One script, run after any wording change:

1. Extract every `<th>` and check for second-person or conversational headings (`You need`, `What to do`).
2. Grep `\b(you|your|yours|yourself)\b` over the whole file. Only Microsoft on-screen strings ("Securing your hardware", "Setting up your device") are legitimate hits.
3. Resolve every internal `Stage n` and `Test n` reference against the actual `<h2>`/`<h3>` list. Renaming Check N to Test N left one `Check 4` reference in the step that sets up the primary control test.
4. Assert every term in the glossary below appears only in its canonical form.

**A retired term quoted inside a rule goes in backticks.** That is what makes the glossary assertion runnable against this README: a bare quoted form is a live use and fails, a backticked one is a citation and is exempt. Assert both files, not just the deliverable.

**Keep a glossary, because a retired-term list cannot find a new split term.** Checking against terms already known to be wrong is what let `USB stick` (3) sit beside `USB drive` (5) through four review rounds: the term had never been wrong before, so nothing looked for it. A generic variant detector was tried and is too noisy to use - it flags every phrase sharing a word. One canonical term per object, asserted as the only form used, is the check that works.

|---|---|---|
| The drive holding the image and the scripts | build USB drive | USB stick, USB key, APM image USB drive, image drive |
| The image file | `Windows11_25H2_PK_Updated_20260827.iso` | the ISO, the image file (in instructions - name it) |
| The security chip and its check | TPM, TPM attestation | security chip, security device |

| Upper-case tag value | upper case | capitals, caps |
| The image installer, Stage 3.1 and 3.2 | Windows Setup | Windows setup screen |
| The post-install screen, Stage 3.3 onward | out-of-box experience (OOBE) | Windows setup screen, setup screens |

**Two screens with one name and opposite instructions is the worst defect this document has carried.** `Windows setup screen` was unambiguous until Stage 3 introduced the installer, and then covered both it and the post-install out-of-box experience - described a paragraph apart, both as a screen asking for language or country, one to be worked through and one not. A technician who worked through the language screens at 3.2 could reasonably do the same at 3.3, creating a local account and breaking the self-deploying enrolment the entire build depends on. Reserve `Windows Setup` for the installer, `out-of-box experience (OOBE)` for everything after it, and assert that neither region names the other's screen.

**Adding a stage can make an existing term ambiguous.** No wording in the old document was wrong; a new object appeared that the old name also fitted. After inserting a stage, list the nouns it introduces and check each against the glossary for a collision, rather than only checking the new text for banned terms.

**A block belongs to the step it describes.** The installer error block sat under 3.3, which is why 3.3 still named `Windows Setup` after the rename. It moved to the end of 3.2, where the install happens.

**Every step that can fail carries a recovery path, and moving a block can remove one.** Relocating the installer block left 3.3 with no escalation at all - the step whose own text names the most consequential mistake available in the build, an account created at OOBE, which no restart clears and which no fault-table row covered. After any block move, assert coverage: each `Stage n` / `n.n` / `Test n` step must contain a `.stop` block, an Action-column table, or inline recovery prose, and a parent Stage may delegate to its children. That audit found four further steps with a pass condition and no action on failure: 5.1 (import returns nothing), Test 3, Test 4 and Test 6. Write the check to accept both child forms, `n.n` and `Test n`, or the parent reports a false positive.

**Assert that every reference to a conditional stage carries its condition - and detect the conditional stages, do not name them.** The check was written for Stage 2 and passed for eight rounds while Stage 4 was equally conditional and none of its dependents carried the condition: Stage 5 told a technician to select a `.csv` that was never produced and then routed them to a hard stop, Stage 6 described a command prompt that was never opened, and two record-sheet rows could not be ticked on the majority path with no annotation to say why. Naming the subject is what made the check useless on the second instance.

Detect by declaration (`Omit this stage`, `is not performed on`, `not required on`), then for every line naming a detected step require its own heading or a conditional construction in either direction (`where it applies`, `where Stage n was omitted`, `where Stage n was performed`, `either path`, `at manufacture`). Currently 3 conditional steps detected - Stage 2, Stage 4, 5.1 - with 0 unqualified references. Exempt open-items rows: they point at a step for context rather than instructing.

**A tool the procedure requires belongs in the kit list, and a third-party tool belongs in the open items.** Rufus was named six times in the preparation steps and appeared nowhere in Prerequisites: no version, no source, no workstation requirement. It was also the only external dependency in the document without an open item, while the ISO source, the network, the instruction sheet and the tenant account all had one. A build facility's SOE may not carry it or may not permit it.

**Check a new setting against the requirements already stated elsewhere in the document.** The preparation section set FAT32's predecessor, NTFS, because it keeps the drive writable for the scripts. Stage 2 requires Secure Boot enabled, 60 lines earlier. Rufus boots NTFS media through its own UEFI:NTFS loader, which Secure Boot commonly refuses, so the two instructions may not have been simultaneously satisfiable and the symptom would have appeared at Stage 3.1 with no entry for it. FAT32 satisfies both. When adding a technical setting, grep the document for the requirements it interacts with rather than optimising it in isolation.

**Every file the procedure handles is named to the character, or it is an open item.** The PowerShell script that `run-CreateMIREGKey.bat` invokes was described only by its relationship to another file, so a technician could not confirm they had received it or that it reached the drive, and the check block could not be completed. A missing script surfaces at Stage 6, after the internal drive has already been erased.

**An orientation paragraph is a claim about the whole document, so a new stage invalidates it.** The overview first said "the build is automated and CompNow does not perform it" and named three tasks; Stage 3 made that false, since installing the image is the longest operator-attended stage at 25 to 40 minutes, the only destructive one, and 15 manual steps. Rewriting it as "CompNow performs four things" then omitted Stage 1 and Stage 9 - and Stage 9 is where the build partner's dispatch and asset-register obligations live, which is the part a supplier most needs stated as theirs. It now names the members and no count.

**An assertion must not contain a bucket for the things it is checking.** The mapping check that was supposed to catch the overview undercount had a `handling` category, into which it put Stages 1, 2 and 9 and passed them. A residual bucket makes an assertion agree with whatever it is given: every stage must map to work the orientation paragraph actually names, or the check has no content. Nine stages, nine mapped, no bucket.

**Append a register row immediately before the table's closing tag, never anchored on a sibling row.** Using an existing row as the `str_replace` anchor prepends rather than appends. This has now happened three times: DR-019/DR-020 between DR-015 and DR-016, A-09 between A-02 and A-03, and open item 7 between 5 and 6 in CN-PK-01 - each time from the same reflex of reaching for the nearest unique string. The unique string to reach for is the table's `END` line, or `</tbody>` in HTML.

**A count check cannot see a permutation, so assert the sequence.** The edit that misplaced open item 7 was verified with `boxes === rows` (7 === 7) and list-tag balance, and both passed. Every ordered column must equal its own sort: register IDs per prefix, record-sheet cells, `Stage n` and `Test n` headings. One pass, one boolean per sequence. An assertion must end in a boolean, and it must be the boolean that can fail.

**Count both sides and compare them; do not report a count.** The same round, a check counted 3 amber boxes against 6 open items and reported "3 amber boxes matching the 6 open items" - a mismatch stated as a match. Three items had no marker at the point they apply, including the image identity at Stage 3, the destructive stage: nothing warned the technician that the media version was unconfirmed before they erased the drive. Every open item now has exactly one marker, all six of the same kind, each in the region its row names.

The lesson is narrow and mechanical: an assertion must end in a boolean, not a number. `boxes === rows` fails; "boxes: 3, rows: 6" reads as agreement to whoever wrote it.

This was the third absolute count in the document to go stale, after `the only divergence` and `exactly two places`, and the rule against it was already written here. A rule in this file did not stop me writing "four things" one round after quoting it; the assertion is what stops it.

**An instruction for the path that skips a step must not live inside that step.** 5.1's escalation carried the only action for a factory-registered device missing from the Autopilot devices list - a device that cannot provision at all - and sat after 5.1's numbered steps, which that reader is told to skip. The action now sits between the Omit note and the steps, so the reader meets it before the point they jump from. Assert the order: within a conditionally-omitted step, the Omit note comes first, then any action for the omitting path, then the steps.

**A step can depend on a conditional step's output without naming it, and the reference assertion will not see it.** 5.2 opened "Verify the tag on every device after import" while the section intro stated 5.2 runs on both paths - and on the factory-registered path there is no import. The check looks for lines naming a conditional step; this line named its *product*. Grep the outputs too: `after import`, `the .csv`, `the prompt from Stage n`. Now "by either path".

**A conditional stage's dependents include whatever it produces, not just its number.** Stage 4 produces two things later steps consume: the `.csv` file and an open command prompt at the USB drive. Both were assumed present. When a stage becomes conditional, list its outputs and find every step that reads one.

**Not every sub-step of a conditional stage is conditional.** Making Stage 5 conditional wholesale would have been wrong: 5.2 and 5.3 apply on both paths, and a device registered at manufacture is *more* likely to arrive without a group tag, so 5.2 matters most on exactly the path that skips 5.1. Qualify at the sub-step, and state which siblings always run.

**Assert the parsed DOM after any scripted region edit, not just the source text.** A `run_script` edit whose `old_string` began inside an `<ol>` and ran past its `</ol>` swallowed the closing tag, and the `new_string` opened a fresh list without closing the original. Every text-level check passed - headings present, references resolving, tag counts never compared - while the unclosed list adopted the remaining 32 elements of the document and `ol{padding-left:19pt}` indented Tests 5 to 7, the fault table, the build record sheet and the open-items table by 25px, narrowing the two tables a technician works from. This is the boundary-spanning `old_string` failure CLAUDE.md warns about, and text assertions structurally cannot see it.

Three checks, after every scripted edit:

1. Source-level tag balance: `<ol`/`</ol>` and `<ul`/`</ul>` counts must match. Cheap, and it catches this before the file is even saved.
2. `[...document.querySelectorAll('ol,ul')].filter(l => [...l.children].some(c => c.tagName !== 'LI'))` must be empty. A list containing a `P` or `H2` is an unclosed list.
3. Every `h2`/`h3` shares one `getBoundingClientRect().left`, and every `table` shares one left and one width. Exempt headings whose parent is a padded container - the `.rule` box's heading sits inset by design.

**A fail condition must not claim more coverage than the steps deliver.** Test 4's block failed on "Writer, Calc or Impress" while its steps opened Writer alone, so the acceptance gate covered one of the three applications it named. This build's own `../research-libreoffice-kiosk.md` is why it matters: Assigned Access generates one AppLocker rule per listed file, so Writer opening proves nothing about `scalc.exe` or `simpress.exe` - and the document calls launch failure the most frequently observed fault on the build. Calc and Impress are now opened by their own steps.

Assert it: every object named in a fail condition must be exercised by a step in the same test. The check is one pass - for each application, compare "opened by a step" against "named in a fail condition" and require they agree.

**When a fail condition acquires a second cause, enumerate the causes.** Test 4's block ended "naming which of the three failed" after a fourth case was added that is not one of the three. It is now a list, one line per cause.

**A test whose pass criterion is an absence needs a gate on the artefact.** Test 7 passed on "the document is no longer present and Downloads is empty", which is exactly what a device shows when nothing was ever saved. Three tests had no fail condition for a missing artefact, so a device could be recorded as passing the session purge test - the primary control the build exists to deliver - without the purge ever being exercised. The artefact is now named (`test.odt`), Test 4 fails if it is not in Downloads after saving, Test 5 fails if it is missing, Test 7 stops rather than records if it is absent, and Test 7 is stated as **void, not passed**, in that case. The record sheet names the artefact in all three rows, so the sheet cannot capture a void test as a tick.

Generalise it: wherever a pass criterion is the absence of something, assert that the thing existed first, and make the absent-precondition case void rather than pass. An absence proves nothing on its own.

**A step that names an outcome without a method is not a step.** Test 5's "confirm the C: drive is not reachable" left the technician to choose how - glancing at the navigation pane, or typing a path into the address bar, which is the case that actually tests the restriction. Two technicians would record different results for the same device. Every verification step gives the keys and the strings: address bar, `C:\`, `Enter`.

**A failure named in prose needs a fault-table row too.** The technician who makes the mistake is not reading the step they made it in; they are reading the fault table. OOBE completed or a local account created is now a row of its own, distinct from the ESP account setup phase failure it superficially resembles.

**Where a set of steps share one consequence, they share one treatment.** The seven acceptance tests all stop dispatch, but recovery paths were added across three rounds and ended up in four different forms: three in red `.stop` blocks, four in plain prose, three stating do-not-dispatch, four not, and the two splits did not even coincide. On a printed sheet a technician learns that red means stop, so two dispatch-blocking failures were invisible. All seven now open `<b>Fail if</b>` in a `.stop` block naming symptom and action, and do-not-dispatch is stated once in the Stage 8 intro instead of in three of seven tests. Assert the set: for each member, the same block type and the same opening construction.

**Adding to a set incrementally is what breaks its uniformity.** Nothing was wrong when each recovery path was written; they were written in different rounds. After adding to any set - tests, stages, register rows - re-assert the whole set rather than checking the new member.

**A stated dependent list must match the steps that actually reference the artefact.** Test 4 said "Test 7 uses it" while Tests 5 and 7 both did. Same plural blind spot as `Stages 3 and 4`: extend the reference assertion to check that a named dependent list matches the steps that really cite it.

**Vendor on-screen strings are exempt and must be quoted exactly.** Three legitimately break the glossary because they are what the technician reads on the screen: `TPM 2.0 / Security Device` (Dell firmware), `Securing your hardware` and `Setting up your device` (Windows). Never normalise a string the reader has to match against a display. Exempt these by literal before asserting the glossary, the same way the contrast guard exempts decorative borders.

**Terminology has to match across a cross-reference, not just within a section.** The fault table sent the reader to Prerequisites for `attestation endpoints` while that table's rows were labelled `Security chip check`. Where one section names another, the term used in the pointer must appear in the target.

**Fix a cross-reference at the rows, not at the column heading.** Correcting the above by renaming the column to `Attestation endpoint` made it false for its own first row, general outbound internet on TCP 443/80, which is not an attestation endpoint. Relabelling the three rows was sufficient on its own. A column heading has to be true of every row under it, so it is the wrong lever for making a pointer resolve.

**Renumber stages mechanically, with the assertion, not by hand.** Inserting the image install as Stage 3 moved six stages and every reference to them. Substitute through placeholders so `Stage 3`&rarr;`Stage 4` cannot collide with `Stage 4`&rarr;`Stage 5`, and note that a sub-heading pattern needs both forms: `>3.1` in a heading and ` 3.1` in prose. Then assert five things: stages run 1..n with no gap, every sub-heading number matches its parent stage, every reference resolves, no stage is orphaned, and every record-sheet and open-items cell resolves.

**Match `Stages? \d+( and \d+)?`, not `Stage \d`.** The single reference reading "Stages 3 and 4 deliver registration" survived both the renumber and the assertion, because the plural has no space after `Stage`. One pattern was wrong in two places at once, so the check confirmed the defect instead of catching it: a renumber and its assertion must never share a pattern that could be wrong.

**When a stage is inserted, re-anchor every path that re-enters the procedure.** Four rebuild paths pointed at the stage that used to be first. Grep `rebuild` and `wipe` and confirm each names the stage a rebuild now starts from - the assertion found a fourth path that review had not reported.

**A stage owns its own entry state; do not rely on the previous stage's exit state.** Stage 3.1 opened "with the device switched off", which was true after Stage 2 and false after Stage 1. Adding a shutdown to Stage 1 fixed one path and left the other broken, because Stage 2 powers the device back up after it. The durable fix was to give 3.1 its own shutdown step, so neither predecessor matters. With a conditional stage in the sequence there is no single predecessor to depend on, and a precondition set upstream can always be undone by whatever runs between.

**A precondition must name every stage that has to be complete, and carry the condition of any stage that is conditional.** Stage 3's warning first named only Stage 1, then was corrected to "Stages 1 and 2 are complete" - which is unsatisfiable on the majority path, because Stage 2 is skipped on the APM-purchased model. It now reads "that Stage 1 is complete, and that Stage 2 is complete where it applies". A precondition the reader cannot satisfy teaches them to ignore it, and this one sits in the block that warns the drive is about to be erased.

**A numbered step must not reference content below its own list.** The Stage 1 shutdown read "once the power-on check below is complete", pointing at blocks after the list it sat in, so the reader had to jump forward and back.

**Every value in the build record sheet's Stage column must resolve to a real heading.** It listed the Stage 7 tests as 7.1 to 7.7, a form appearing nowhere else, so a technician carrying the sheet back to the procedure had nothing to look up. Assert each cell against the `<h2>`/`<h3>` list, the same check as prose cross-references: a record sheet is a set of references too.

**Making a stage conditional changes who reads it, so its content has to change too.** Stage 2 became "not performed on the APM-purchased model", which left every instruction under it (`F2`, the Dell firmware search box, Dell menu paths) addressed only to technicians using a different vendor's hardware. The entry key is now given as a range and the table column is headed `Dell menu path`, with the instruction to locate each setting by name rather than by path.

**A conditional stage also needs a route back in.** Skipping Stage 2 removed the only path to it, and `0x800705B4` - the one fault that requires it - did not name it. Assert that every stage is referenced at least once outside its own heading; an orphaned stage is unreachable for the reader who needs it most.

**Two CSS faults a source read cannot see.** Both only appear once rendered, so the mechanical sweep above must be paired with a rendered check:

- **A label rule that matches every descendant.** `.see b {display:block; text-transform:uppercase}` was written for the block's label but matched any inline `<b>` inside it, so Stage 6's two Microsoft screen names became full-width uppercase label rows and broke the sentence into five lines. Scope a label to `> b:first-child`. Same latent fault existed in `.tbc b`.
- **A floated badge overlaps a following filled block.** `.time {float:right}` looks correct beside transparent prose, which wraps around it, but sits on top of the next sibling's background when that sibling has a fill. Every filled-block class plus `table` carries `clear:right`, not only the ones observed to break.

**Rendered check, after any CSS change:** assert every `.see b`/`.tbc b` that is not `:first-child` computes `display:inline`, and assert no `.time` rect intersects any filled block's rect.
