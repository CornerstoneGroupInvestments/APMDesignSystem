H2 |1.1 Purpose
P |The purpose of this document is to provide the detailed logical and physical architecture for the deployment of **YubiKey 5C NFC FIPS hardware security keys** as the phishing-resistant authentication method for privileged access across APM, and to define the identity, endpoint, session and service-management components required to implement it.
P |The design enables the project team and APM administrators to authenticate to high-privileged (xy) and privileged (zz) accounts, jump boxes, virtual machines, the privileged Azure Virtual Desktop (AVD) image, Windows App, the Azure Portal and Microsoft 365 admin portals using a FIPS-validated, hardware-bound passkey - from both APM-managed and personal devices - with no password used or exposed at any point in the flow.

H1 |2. Overview
P |APM is standardising end-user computing on Azure Virtual Desktop, orchestrated through Nerdio Manager for Enterprise and managed by Microsoft Intune and Microsoft Entra ID. The Privileged Access use case within that program introduces a hardened, Privileged Access Workstation (PAW)-style AVD image as the **only path to production systems**, operated at two tiers: Priv (account prefix zz) and High-Priv (account prefix xy).
P |Passwords - even when combined with app-based multi-factor authentication - remain phishable. A proxied, adversary-in-the-middle sign-in page captures the password and the approval together, and the attacker inherits the session. For accounts that can change tenant configuration or reach production data, APM requires an authenticator that cannot be phished, replayed or exported.
P |The **YubiKey 5C NFC FIPS** provides exactly that. It is a FIPS 140-2 and FIPS 140-3 validated hardware authenticator implementing FIDO2 / WebAuthn, in which the private key is generated inside a tamper-resistant secure element, is cryptographically bound to the legitimate sign-in origin, and can only be used with the holder's PIN plus a physical touch. There is no shared secret, no seed, no certificate file and no password hash for an attacker to steal.
P |The solution is deliberately simple for the user. The key arrives, the user completes a short identity verification call, they sign in once using a Temporary Access Pass, and Microsoft Entra ID prompts them to register the key as part of that sign-in. They set a PIN and touch the key. From that moment, signing in means inserting the key (or tapping it over NFC), entering the PIN and touching it. Registration uses native Entra ID functionality only - no third-party software, agents, middleware or portals are introduced anywhere in the design.

H2 |2.2 Guiding Principles
P |The following principles drive how this solution is designed, implemented and operated.
TBL |2400,6960
TH |Principle||What it means in this design
TR |Phishing-resistant by default||Privileged accounts never use a password or a phishable second factor. The credential is origin-bound and hardware-bound, so there is nothing a user can be persuaded to type, approve or forward.
TR |Assume endpoint compromise||The design must remain safe when the endpoint is untrusted. Neither the credential nor the production environment may depend on the integrity of the device in the user's hands.

TR |Least privilege, just in time||No standing administrative rights. Privilege is activated per tier, time-boxed, justified and audited.

TR |Operable at APM scale||Privileged staff are distributed nationally. Postal issuance is supported as a first-class path, with identity verification controls that make interception worthless.
TR |Evidence by design||Every control produces an artefact an assessor can read - policy export, key register, PIM audit history, monthly reporting - to support RFFR and ISO 27001 assessment.

H2 |3.4 Gap treatment
P |One capability gap is carried. **macOS local (login-window) sign-in cannot use FIDO2 natively.** macOS users authenticate to Entra ID, AVD and all administrative portals with the YubiKey through WebAuthn in the browser and in Windows App, but the local Mac login continues to use the local account credential.
P |This does not weaken the production path. Privileged work occurs inside the AVD boundary, and the AVD session is entered with the hardware key regardless of how the Mac itself was unlocked. A compromised local Mac account confers no privileged access, because the zz and xy accounts are separate from the local account and cannot be used without the key.
P |Two treatment options are available and are recorded as future work rather than being adopted now, to keep the approval scope tight: PIV smart-card login using the same key's PIV applet, and Microsoft Entra Platform SSO for macOS. Either can be added later without changing this design.
H1 |4. Application Architecture
P |The application architecture for this solution is built entirely from existing, licensed Microsoft platform components plus one hardware component. No new software is purchased, no application is built, and no component is deployed into APM's own infrastructure. This is a deliberate design decision: the assurance case is simpler and stronger when the authentication path introduces no new code, no new agent and no new supply chain.

H3 |5.1.4 Registration standard - the native Entra ID prompt at sign-in
P |Registration deliberately uses only built-in Entra ID behaviour, because it is both the simplest flow for the user and the easiest for Cyber Security to assure. When a user who is targeted by the passkey policy signs in with a Temporary Access Pass and has no passkey registered, **Entra ID interrupts the sign-in and guides them through registering the key**: insert or tap the key, set a PIN, touch the key, confirm. The user never visits a separate portal and installs nothing. The TAP is consumed by that same sign-in.
P |Three properties make this acceptable to a security reviewer. The registration session can only be established with a Temporary Access Pass issued after live identity verification, or with an existing registered passkey. The authenticator presented must pass attestation and match the AAGUID allow-list. And every registration writes an audit event that is alerted on and reconciled against the key register. The full operational procedure is specified in section 9.1.

H2 |5.2 Integration standards and patterns
P |Authentication must reach beyond the initial sign-in and into the session, because a privileged administrator working inside the AVD image will be prompted again - by the Azure Portal, by PIM activation, and by jump boxes. The integration pattern that makes this work without weakening the boundary is **WebAuthn redirection**.

TR |In-session WebAuthn redirection||Enabled on the privileged host pool. A passkey prompt raised inside the AVD session is redirected over the RDP channel to the key attached to the local endpoint, so the same physical key satisfies both the session sign-in and the in-session prompt

H2 |5.3 Network &amp; Infrastructure Standards &amp; Patterns
P |Figure 4 shows where the solution sits relative to APM's networks and the Azure Australia East hub-and-spoke landing zone.
FIG |network-authentication-paths.png|Figure 4. Network and infrastructure - authentication paths|3040|1600
P |The authentication path has **no dependency on APM's corporate network**. Both the identity endpoint and the AVD gateway are internet-facing Microsoft services reached over outbound TLS 443. No inbound port is opened on any APM network, no VPN is required, and no site-to-site tunnel is a prerequisite for privileged sign-in.
P |This is a deliberate architectural choice with a direct security benefit: trust is established by the hardware key and by Conditional Access, not by network location. It also removes a class of availability risk, because an administrator responding to an incident can authenticate and reach the PAW from any transport, including a mobile hotspot, without first restoring corporate connectivity.
P |Inside Azure, the privileged AVD host pool attaches to the landing zone as a peered spoke. Administrative hops to production jump boxes and virtual machines occur wholly within Azure private networking, subject to the network security group and private endpoint standards defined by the landing zone design. Telemetry from every layer flows to the Log Analytics workspace and Microsoft Sentinel.

H1 |7. Cyber &amp; Security Architecture
H2 |7.1 Why FIDO2 on FIPS-validated hardware
B |**Phishing-resistant by protocol.** The WebAuthn assertion is cryptographically bound to the origin and to a per-authentication nonce. A proxied fake sign-in page receives an assertion that is invalid for the real origin. There is nothing the user can be tricked into typing, approving or forwarding
B |**Hardware-bound.** Private keys are generated inside, and never leave, the FIPS-validated secure element. Malware on any endpoint can neither read nor clone the credential
B |**User verification and user presence.** Every use requires the PIN (something you know) and a physical touch (presence). A stolen key alone is useless, and malware cannot invoke the key silently
B |**Validated cryptography.** Firmware 5.7.4 is FIPS 140-3 certified at Overall Level 2 with Physical Security Level 3; firmware 5.4.3 is FIPS 140-2 certified. Both meet NIST SP 800-63B AAL3
B |**Replay- and export-proof.** Assertions are single-use. There is no OTP seed, no certificate file, no password hash and no recovery code for an attacker to obtain

H2 |7.4 The personal device question - why BYOD access is safe in this design
P |Permitting privileged sign-in from personal devices is the aspect of this design most likely to attract challenge, so the argument is made explicitly rather than left implicit. The design's position is that **the endpoint is not trusted and does not need to be trusted**, because the credential and the environment are each protected independently of it. Figure 8 shows the resulting boundary.
FIG |trust-boundary-byod.png|Figure 8. Cyber architecture - trust boundary and device posture|3040|1600
B |**The credential cannot be stolen from the device.** There is no password to keylog, no seed to extract and no exportable key. The private key is in the YubiKey, not in the device, and no software path exists to retrieve it
B |**An attacker present on the device cannot authenticate.** PIN entry plus a physical touch defeat remote invocation, and origin binding defeats any phishing page presented to the user
B |**The device never touches APM data.** CA-APM-PRIV-04 restricts personal devices to the AVD entry point. Within the session, drive, clipboard, print and USB redirection are disabled, watermarking and screen capture protection are enabled, and nothing is written to the endpoint
B |**Session tokens are bounded.** An 8-hour sign-in frequency with no persistent browser session, plus continuous access evaluation, limits the value of any token that could be captured
B |**What remains is session observation.** A fully compromised personal device could capture what the administrator sees on screen. This residual risk is recorded as R-02: it is time-boxed by PIM, watermarked for attribution, monitored in Sentinel, and materially smaller than the risk it replaces - a phishable credential usable by anyone, from anywhere, invisibly
B |**Consistency with existing posture.** This is the same boundary argument APM already accepts for BYOD access to the Standard User AVD channel, strengthened here by hardware-only authentication, just-in-time elevation and the PAW image's egress controls

H1 |8. Service Availability and Disaster Recovery
H2 |8.1 Business Service Tiering
P |Privileged authentication is a **Tier 1** capability. Its loss does not stop business operations directly, but it delays incident response and blocks production change, which makes it business-critical in exactly the circumstances where it matters most.
P |The dependency chain is deliberately short: Microsoft Entra ID, subject to the Microsoft service level agreement, plus the physical key in the user's possession. No new APM-operated infrastructure is introduced, so the solution adds no new availability liability beyond the key itself and the processes that replace it.
H2 |8.2 Service Availability
B |Entra ID authentication availability and AVD availability are inherited from the existing platform design in Australia East, and are unchanged by this solution
B |Each High-Priv (xy) holder registers **two keys** - a primary and a spare. The spare is stored under the holder's site security arrangement. Priv (zz) holders may hold a single key, with the 24/7 Temporary Access Pass path as their fallback
B |Temporary Access Pass re-issuance is available 24/7 through the existing on-call process, using the same identity verification controls as first issuance
B |Revocation is available 24/7 and takes effect within one hour of report, independent of whether the physical key is recovered
H2 |8.3 Disaster recovery &amp; Resilience
B |**Break-glass.** Two cloud-only emergency access accounts are excluded from CA-APM-PRIV-01 to 05. Each has two registered FIDO2 keys held in safes at separate sites. Any sign-in raises a Microsoft Sentinel incident to Cyber Security. The accounts are tested and reviewed quarterly
B |**Tenant-level Entra ID outage.** Privileged authentication is unavailable along with the rest of the tenant, and recovery follows the Microsoft major incident process. No APM-side credential fallback is created - deliberately - because any such fallback would re-introduce the phishable path this design exists to remove
B |**Key fleet failure, such as a batch defect.** Dual-firmware acceptance (5.4.3 and 5.7.4) means a replacement batch can be sourced and registered within days through the standard lifecycle. Break-glass covers the interim for tenant-critical action
B |**Loss of the key register.** The register is an operational convenience, not a control of last resort: revocation is performed in Entra ID against the user object and does not depend on knowing the serial number
H1 |9. Service Management
H2 |9.1 Service Management principles
P |The service is operated on four principles: issuance is never faster than identity verification; revocation is always faster than investigation; the register must reconcile to the platform, not the other way round; and no support path may ever restore access by weakening authentication. Figure 9 shows the resulting lifecycle.
FIG |key-lifecycle.png|Figure 9. Service management - key lifecycle|3040|1440
P |The issuance procedure, including the postal path, is as follows.
NUM |The requester's manager raises the ServiceNow request. Cyber Security approves privileged issuance. A key serial is assigned from stock and recorded in the register against the user.
NUM |The key is issued in person where the user is co-located with IT; otherwise it is sent by tracked post to the user's verified address. The key carries no credential in transit, so interception yields inert hardware.
NUM |On receipt the user books the verification call. The Service Desk verifies identity against the privileged verification script - video call with photo identification, or manager attestation - and confirms that the key serial matches the register.
NUM |The Service Desk issues a one-time Temporary Access Pass with a one-hour lifetime. The user signs in at any Entra ID sign-in surface using the pass, and Entra ID prompts passkey registration as part of that sign-in. The user sets a PIN of at least eight characters, with complexity enforced by the key hardware, and touches the key.
NUM |Entra ID validates the attestation certificate and the AAGUID. Only a genuine YubiKey 5 FIPS Series key completes registration. The register is updated to Active. From the next sign-in, Conditional Access enforces key-only authentication for that account.
NUM |On loss, theft or departure, the report triggers deletion of the passkey in Entra ID within one hour. This deletion is the authoritative revocation - the key becomes inert whether or not it is recovered. The register is updated and a replacement follows steps 1 to 5. Returned keys are FIDO2-reset before restocking.
